# Glossary

| Term | Definition | Avoid |
|---|---|---|
| Operator | The one person who builds, configures and runs Slussen on their own phone and owns the household's budgets in the Budget App. Each installation has exactly one operator. | end user, client |
| Adopting Developer | A developer who clones the public repository and builds Slussen for their own household, and then becomes the operator of that build. | contributor, integrator |
| Budget App | The external budgeting application that is the system of record for the household's transactions and that Slussen writes to. This build supports one Budget App; it is replaceable by design. | destination, ledger, budgeting app, target |
| YNAB | The Budget App supported in this build. The name is used only where a rule depends on YNAB's own behaviour; everywhere else the generic term Budget App is used. | |
| Budget | One workspace in the Budget App with a single currency, holding Budget Accounts. The operator may have several budgets in different currencies. | |
| Budget Account | One of the places inside a Budget in the Budget App that hold transactions and a balance. It receives the transactions of at most one Bank Account, or it is a Manually Kept Account. Always written in full as Budget Account (or as a glossary compound such as Manually Kept Account), never shortened to its last word, because the short form cannot be told apart from Bank Account. | destination account, ledger account |
| Manually Kept Account | A Budget Account that no source exposes and that the operator maintains by hand in the Budget App; Slussen does not write to it. | |
| Budget App Transaction | A transaction in a Budget Account as Slussen last read it from the Budget App, including whether it has since been deleted or merged there. Slussen keeps a stored copy of these to compare against and to show when the Budget App cannot be reached. | |
| Matching Date Window | The number of days before or after a Bank Transaction's date within which the Budget App pairs an Import with a Typed Entry of the same amount; Slussen uses the same window to find a Match for a Typed Entry and a Possible Import by another path. For YNAB it is 10 days. | |
| Data Provider | An external online service from which Slussen fetches transactions and balances of the operator's Bank Accounts. This build has two: SimpleFIN and Enable Banking. Data Providers are extensible by design. | feed provider, aggregator, bank API, source provider |
| File Format | A supported layout of a transaction file downloaded from a bank, which Slussen can import. Each File Format declares whether its transactions carry a Stable Reference, derive one from their own fields, or have none, and declares its own Upload Window. This build supports one. | CSV format, export type |
| Source | Where a transaction comes from: a Data Provider or an imported Transaction File. | origin |
| Source Key | The fixed name of a Data Provider or File Format that enters every Import Identifier it produces. A Source the Predecessor App had keeps the key the Predecessor App used. | |
| Transaction File | A file of transactions that the operator downloaded from a bank and imports into Slussen for a Bank Account that has no usable transaction feed. | CSV, export file |
| Bank | A financial company that holds one or more of the operator's Bank Accounts and is reached through a Data Provider or a Transaction File. | institution, ASPSP |
| Bank Account | One place at a Bank where the operator (or a household member) keeps money or a credit line, such as a checking, savings or credit card Bank Account, as exposed by a Source. Always written in full as Bank Account (or as a glossary compound such as Account Mapping, Account Balance or Retired Account), never shortened to its last word, because the short form cannot be told apart from Budget Account. | source account, feed account |
| Bank Account Identity | The fixed identity of a Bank Account, set in the Build Configuration and never changed, that enters every Import Identifier of its transactions. A Bank Account the Predecessor App had keeps the identity the Predecessor App gave it. It is not the identifier a Data Provider gives the Bank Account. | |
| Account Mapping | The configured link from one Bank Account to one Budget Account. It is locked once a transaction has been sent through it. | binding, account link |
| Retired Account | A Bank Account whose Account Mapping the operator has switched off. It is neither fetched nor uploaded, keeps its identity and history, and can be restored. | deleted account, tombstone |
| Bank Consent | The bank's permission, granted by the operator through the bank's Strong Customer Authentication, that lets Slussen read a Bank Account through a Data Provider until it expires. | authorization, consent token |
| Consent Request | One attempt to grant or renew a Bank Consent, started by Slussen with a Data Provider for one Bank. It is valid for at most 15 minutes, can be answered once, and only the most recent one for a Bank is accepted. | |
| Strong Customer Authentication | The bank's own identity check (for example BankID) that the Bank Account holder completes to grant or renew a Bank Consent. | SCA, login |
| Fetch | An operator-started read of transactions and balances from one Data Provider. A fetch never writes to the Budget App. | sync, pull, refresh |
| Fetch Result | The outcome of one Fetch for one Bank Account: fetched, failed, not consented, not recognised, or ambiguous Bank Account. | |
| Bank Transaction | One booked transaction of a Bank Account as delivered by a Source. | row, bank row |
| Stable Reference | An identifier of a Bank Transaction that stays the same every time the transaction is delivered and is unique within its Bank Account: either given by the Source, or derived by a File Format from the transaction's own fields. Two transactions that would get the same derived reference have no Stable Reference. | transaction id |
| Import Identifier | The identifier Slussen derives for each Bank Transaction from the Source Key, the Bank Account Identity and the Stable Reference, and sends with the transaction, so that the Budget App and Slussen can recognise it again. A deliberate Re-upload gets a new one. | |
| Typed Entry | A transaction the operator entered by hand in the Budget App. | manual entry, user-entered transaction, manual transaction |
| Import | A transaction in the Budget App that was created by an import path (Slussen or another importer) and carries that path's Import Identifier. | imported row |
| Other Import Path | Any importer other than Slussen and the Predecessor App that writes to the Budget App, including the Budget App's own bank import. | external importer, other tool |
| Comparison | Slussen's check of each Bank Transaction against what the Budget App already holds, including what was deleted or merged there, that gives the transaction its Status. | reconciliation, classification, verdict |
| Transaction Status | The result of the Comparison for one Bank Transaction. The statuses are New, Match For Typed Entry, Already In Budget App, Possible Import By Other Path, Deferred, Deleted In Budget App, Merged In Budget App, Decision No Longer Holds, Needs Review, Too Old, In The Future, Outcome Unknown, Transfer Leg, Guessed Transfer, Held Transfer, Arrived As Transfer Counterpart and Transfer Counterpart Changed. | label |
| Needs Review | The Transaction Status of a Bank Transaction that has no Stable Reference or that its Source could not interpret; it waits for the operator's Review Decision. | |
| Decision No Longer Holds | The Transaction Status of a Bank Transaction whose Already Present decision named a Budget App Transaction that was since deleted, moved to another Budget Account or changed in amount; it goes back to the operator for review. | |
| Outcome Unknown | The Transaction Status of a Bank Transaction that Slussen sent without learning whether the Budget App created it; it stays available for upload under the same Import Identifier. | |
| Held Transfer | The Transaction Status of both Transfer Legs of a Transfer that the operator holds back; neither is uploaded until the operator changes the decision. | |
| Arrived As Transfer Counterpart | The Transaction Status of a Bank Transaction that arrives for the side of an uploaded Transfer whose Transfer Counterpart the Budget App already holds; it is not uploaded again, and the Transfer Counterpart is marked cleared. | |
| Transfer Counterpart Changed | The Transaction Status of a Bank Transaction whose Transfer Counterpart was changed or unlinked in the Budget App; it goes to the operator for review instead of being held back. | |
| Eligible Transaction | A Bank Transaction that will be uploaded when the operator confirms the Upload Plan: a new transaction, a match for a Typed Entry, a Transfer Leg that writes its Transfer, or one whose earlier outcome is unknown, after the operator's decisions. | |
| Review Decision | The operator's choice for a doubtful Bank Transaction: already present, import anyway, defer, or re-upload one deleted in the Budget App. A Review Decision can be changed until upload. | resolution, override |
| Upload Plan | The reviewed statement of exactly what Slussen will write: Budget, Budget Accounts, number of transactions, total inflow and total outflow, the Transfer Counterparts it marks cleared, and its expiry. | batch, plan of record |
| Upload | Slussen's write of the transactions of a confirmed Upload Plan to the Budget App. | push, post |
| Upload Window | The bounded date range inside which a Bank Transaction may be uploaded; transactions outside it are shown as too old or in the future. Transactions from a Transaction File use the Upload Window their File Format declares. | age gate |
| Sent Record | Slussen's own durable record of every transaction it has sent to the Budget App, which survives a reinstall and is the basis of exactly-once. | upload log |
| Transfer | A movement of money between two of the operator's Bank Accounts in the same Budget and currency, such as a card payment or a move between Bank Accounts. | internal transfer, transfer pair |
| Transfer Leg | One of the two sides of a Transfer, in one Bank Account: the outflow side or the inflow side. | half |
| Transfer Decision | The operator's choice for a Transfer: confirm it, split it into ordinary transactions, hold it back, or choose the other Budget Account it belongs to. It can be changed until a Transfer Leg is uploaded. | |
| Transfer Description | A text, set in the Build Configuration, whose presence in the payee or memo of a Bank Transaction (compared without regard to case) marks the transaction as a card payment or a bank transfer between two of the operator's Bank Accounts. | |
| Lonely Transfer | A Transfer of which only one Transfer Leg has arrived from its Source so far. | one-sided transfer, orphan leg |
| Transfer Counterpart | The other side of a Transfer that the Budget App creates itself when Slussen uploads one Transfer Leg as a linked transfer. | mirror, auto side |
| Guessed Transfer | A Transfer that Slussen proposes but cannot pair unambiguously, which needs the operator's confirmation before it is uploaded. Also the Transaction Status of its Transfer Legs until then. | suspect, uncertain pair |
| Account Balance | The balance of a Bank Account as reported by its Data Provider, shown next to the Budget Account's balance in the Budget App. | |
| Source Health | The outcome of the last Fetch of a Data Provider or Bank Account, or of the last Transaction File import of a file-imported Bank Account, shown separately from how old its data is. | status dot |
| Freshness | How old the data of a Source or Bank Account is, measured from the time of its last successful Fetch, or for a file-imported Bank Account from the time of its last imported Transaction File. | staleness |
| Blocked Reason | The reason Slussen cannot fetch from or upload to a Bank Account or Source, shown together with the action that removes it. | error state |
| Back-off | A period during which Slussen does not contact a Data Provider or Bank because the provider asked it to wait or a transient failure occurred. | throttling |
| Fetch Cooldown | A period after a successful Fetch of a Data Provider during which a new Fetch of that Data Provider is served from what was already fetched, without contacting it. | |
| Operator Setting | One of the values the operator can change inside the app: Upload Window, Fetch Cooldown, transfer detection, transfer pairing days, Lonely Transfer grace period, outdated-balance limit, Decision Journal on or off and its size limit, and Detailed Logging. Values set in the Build Configuration are not Operator Settings. | |
| Decision Journal | Slussen's on-device record of what it fetched, what it concluded, what the operator overrode, and what later happened to each Import in the Budget App. | audit log |
| Decision Journal Entry | One event recorded in the Decision Journal, such as a session start, a Bank Transaction seen, a Transaction Status changed, an operator decision, an Upload Plan, an Upload or a Budget App outcome. | |
| Journal Export | A file the operator saves outside the app that holds the Decision Journal together with the Budget App's current transactions, for review outside the app. | dump |
| Detailed Logging | An operator-switched mode in which diagnostic logs on the device may contain transaction data and Bank Account numbers for troubleshooting. Credentials and bank sessions are never logged, even then. | debug mode, verbose logging |
| Configuration Template | A file in the repository that shows an adopting developer which Bank Accounts, credentials and settings a build needs and where to get them, without holding real values. | sample config, example config |
| Build Configuration | The operator's own Bank Accounts with their Bank Account Identities, Budgets, Account Mappings, Transfer Descriptions, daily request limits and service credentials, kept outside the repository and included in the app when it is built. | secrets file, local config |
| Predecessor App | The private Android app that Slussen replaces on the operator's phone. | old app, legacy app |
