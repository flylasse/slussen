# Requirements: Slussen

Requirements catalog for Slussen, derived from `docs/vision.md`. Roles are the **operator** and the **adopting
developer** as defined in `docs/glossary.md`. Domain terms follow the glossary.

## Functional Requirements

| ID     | Title                                   | User Story | Priority | Status |
|--------|-----------------------------------------|------------|----------|--------|
| FR-001 | Fetch on Demand                         | As an operator, I want to start a fetch of transactions and balances from one source myself so that Slussen contacts a bank only when I ask it to. | High | Open |
| FR-002 | No Automatic Fetch                      | As an operator, I want Slussen never to fetch, compare against the Budget App or upload on its own, in the background or on a schedule so that every bank access and every write is one I started. | High | Open |
| FR-003 | Open on Stored Data                     | As an operator, I want Slussen to open showing the transactions, statuses and balances it last stored, without contacting any source so that opening the app costs no bank access. | Medium | Open |
| FR-004 | Booked Transactions Only                | As an operator, I want only booked bank transactions to be taken in, and pending ones left out until they are booked so that a transaction is brought in once, in its final form. | High | Open |
| FR-005 | Skip Zero-Amount Transactions           | As an operator, I want bank transactions with an amount of zero to be left out so that the Budget App receives no empty transactions. | Low | Open |
| FR-006 | Import a Transaction File               | As an operator, I want to import a transaction file I downloaded from my bank, for an account that has no usable transaction feed, so that its transactions reach the Budget App without typing them. | High | Open |
| FR-007 | Reject a Faulty Transaction File        | As an operator, I want a transaction file that cannot be read completely to be rejected as a whole, with the reason shown, while the transactions from my previous import stay unchanged so that a faulty file never brings in part of its transactions. | High | Open |
| FR-008 | Balance for a File-Imported Account     | As an operator, I want the balance of an account whose transactions come from a file to be fetched from a Data Provider where one reports it so that I can still compare that account's balance with the Budget App. | Medium | Open |
| FR-009 | Review Transactions Without Stable Reference | As an operator, I want every bank transaction whose source gives it no stable reference, including two transactions from a file that cannot be told apart, to be shown to me for review instead of being merged, guessed or lost so that no transaction is silently dropped or duplicated. | High | Open |
| FR-010 | Grant Bank Consent                      | As an operator, I want to grant Slussen consent to read my accounts at a bank by authenticating once per bank with the bank's own Strong Customer Authentication, started from my phone, so that Slussen can fetch from that bank until the consent expires. | High | Open |
| FR-011 | Renew Bank Consent                      | As an operator, I want to renew a bank consent the same way I granted it, from any place in Slussen that shows the consent is expiring or expired, so that I can restore access without searching for the action. | High | Open |
| FR-012 | Warn of Expiring Consent                | As an operator, I want every opening of the app to show each bank consent that expires within 7 days, with its expiry date and the action that renews it, without blocking any fetch, so that I can renew it before access lapses. | High | Open |
| FR-013 | Hold Back Banks Without Consent         | As an operator, I want Slussen to skip every bank whose consent has expired or was never granted, without contacting it, while other banks of the same Data Provider are still fetched, so that no bank access is spent on a request that will be refused. | High | Open |
| FR-014 | Honour a Request to Wait                | As an operator, I want Slussen to wait as long as a bank or Data Provider asks before contacting it again, even when I start a fetch myself, so that Slussen does not trigger further refusals or put my bank consent at risk. | High | Open |
| FR-015 | Retry After a Transient Failure         | As an operator, I want Slussen to wait 30 minutes after a timeout, an outage or an unreadable answer from a source before fetching from it again, unless I start the fetch myself, so that a passing failure is retried without repeated failed calls. | Medium | Open |
| FR-016 | Fetch Cooldown After Success            | As an operator, I want a fetch of a source that succeeded within the last 60 minutes, a number I can change or switch off, to be answered from what was already fetched without contacting the source so that repeated presses do not spend bank access. | High | Open |
| FR-017 | Daily Request Limit per Data Provider   | As an operator, I want Slussen to stop contacting a Data Provider for the rest of the day once its daily number of requests (24 by default) is reached, and to show that this is the reason, so that Slussen stays within the Data Provider's own limit. | Medium | Open |
| FR-018 | Isolate Source Failures                 | As an operator, I want a failure in one source or one account to leave the fetch, comparison and upload of every other source and account unaffected so that one broken bank does not stop the rest. | High | Open |
| FR-019 | Compare With the Budget App             | As an operator, I want each fetched bank transaction compared with what the Budget App already holds, including transactions deleted or merged there, and given a transaction status so that I can see per transaction whether it is new or already there. | High | Open |
| FR-020 | Send Matches for Typed Entries          | As an operator, I want a bank transaction that matches an entry I typed in the Budget App (same account, same amount, within the Budget App's matching date window) to be shown as a match and sent on upload so that the Budget App pairs the two instead of holding both. | High | Open |
| FR-021 | Hold Possible Imports by Another Path   | As an operator, I want a bank transaction that resembles an import created by another import path in the same account (same amount, within the matching date window) to be held back from upload until I decide so that a likely duplicate is never written without my decision. | High | Open |
| FR-022 | Decide on a Possible Import by Another Path | As an operator, I want to decide for each held transaction that it is already present (choosing the exact Budget App transaction from a list showing date, payee, amount and account when there are several), that it is imported anyway, or that it is deferred so that every collision is resolved by me and never silently. | High | Open |
| FR-023 | Recheck an Already-Present Decision     | As an operator, I want my decision that a transaction is already present to be checked again on every comparison, and the transaction returned to me for review when the chosen Budget App transaction was deleted, moved to another account or changed in amount, so that my decision never hides a transaction permanently. | High | Open |
| FR-024 | Keep Deferred Transactions Held         | As an operator, I want a deferred transaction to stay held back across later fetches, even when the resembling import disappears, until I decide otherwise so that a deferral is never undone without me. | Medium | Open |
| FR-025 | Recognise Own Uploads                   | As an operator, I want transactions Slussen itself sent to the Budget App never to be treated as imports by another import path so that my own earlier uploads do not hold back new transactions. | High | Open |
| FR-026 | Show Transactions Deleted in the Budget App | As an operator, I want a bank transaction that Slussen sent and that I later deleted in the Budget App to be shown as deleted there and not sent again so that a deletion I made is respected. | High | Open |
| FR-027 | Show Transactions Merged in the Budget App | As an operator, I want a bank transaction that the Budget App merged into an entry I typed to be shown as merged and not sent again so that a completed pairing is not mistaken for a loss. | Medium | Open |
| FR-028 | Re-upload a Deleted Transaction         | As an operator, I want to choose, per transaction and off by default, to upload again a transaction that was deleted or merged in the Budget App or whose already-present decision no longer holds, as a new transaction, so that I can recover a transaction I deleted by mistake. | Medium | Open |
| FR-029 | Change Decisions Until Upload           | As an operator, I want to change or clear each review decision and transfer decision until the transaction is uploaded, after which it is locked, so that I can correct a mistake before anything is written. | High | Open |
| FR-030 | Upload Date Window                      | As an operator, I want only transactions dated within the upload window, by default the last 7 days and adjustable by me, and not in the future, to be uploaded, and every transaction outside the window shown as too old or as in the future so that old or future-dated transactions never disappear silently. | High | Open |
| FR-031 | Age Out Visibly                         | As an operator, I want a transaction that leaves the upload window while it waits for my review to stay visible with the reason it can no longer be uploaded so that a transaction I have not handled is never lost without notice. | High | Open |
| FR-032 | Block Accounts With a Currency Mismatch | As an operator, I want an account whose source currency differs from its Budget's currency to be blocked from upload and its balance comparison hidden, with the reason shown, so that no amount is ever converted or written in the wrong currency. | High | Open |
| FR-033 | Prepare an Upload Plan                  | As an operator, I want to prepare an upload plan for one Budget or one account that states the Budget, the accounts, the number of transactions to create and to match, the total inflow and total outflow, every transfer counterpart that will be marked cleared, and when the plan expires so that I know exactly what will be written before I confirm. | High | Open |
| FR-034 | Upload Only on Confirmation             | As an operator, I want Slussen to write to the Budget App only when I confirm an upload plan so that nothing is written without my explicit confirmation. | High | Open |
| FR-035 | Write Exactly What Was Confirmed        | As an operator, I want Slussen to check the Budget App, the fetched transactions and the configuration again immediately before writing, and to write nothing and return me to review when any of them changed or the plan expired, so that what is written is exactly what I confirmed. | High | Open |
| FR-036 | Pause Other Work While a Plan Is Open   | As an operator, I want fetching and configuration changes to be unavailable while an upload plan waits for my confirmation, with only confirm, cancel and review decisions allowed, so that the plan cannot change under me. | High | Open |
| FR-037 | Truthful Upload Outcome                 | As an operator, I want to be told per account which transactions were written, which were not, and which have an unknown outcome, and never to see an unconfirmed write as done, so that I know the true state of the Budget App. | High | Open |
| FR-038 | Resend Safely After an Unknown Outcome  | As an operator, I want transactions whose upload outcome is unknown to stay available for upload, and a later upload of them to create nothing that already arrived, so that a lost connection never causes a duplicate or a gap. | High | Open |
| FR-039 | Updated Statuses After Upload           | As an operator, I want the statuses of all transactions in the uploaded Budget to be updated from the Budget App right after an upload so that uploaded transactions are not offered for upload again. | Medium | Open |
| FR-040 | Re-read the Budget App                  | As an operator, I want to have Slussen read the Budget App again and update every transaction status without fetching from any bank so that changes I made in the Budget App show up without spending bank access. | Medium | Open |
| FR-041 | Exactly-Once Sent Record                | As an operator, I want Slussen to keep its own durable record of every transaction it has sent, and to use it to send each bank transaction to the Budget App at most once, even after a retry, timeout, crash, reinstall or re-mapping of an account, so that no duplicate is ever created by Slussen. | High | Open |
| FR-042 | Survive a Reinstall                     | As an operator, I want my account identities, my review and transfer decisions and the sent record to be restored after Slussen is reinstalled, while bank consents are not restored and must be granted again, so that a reinstall creates no duplicates and exposes no bank access. | High | Open |
| FR-043 | Clean Takeover From the Predecessor App | As an operator, I want transactions that the predecessor app already uploaded to be recognised as already in the Budget App so that replacing the predecessor app creates no duplicates. | High | Open |
| FR-044 | Imported Transactions Arrive Cleared    | As an operator, I want every transaction Slussen creates in the Budget App to arrive cleared and not yet approved so that I approve each one in the Budget App without having to clear it. | Medium | Open |
| FR-045 | Switch Transfer Detection On or Off     | As an operator, I want to switch transfer detection on and off, off by default, so that without it every transaction is imported as an ordinary transaction. | Medium | Open |
| FR-046 | Detect Transfers Between Own Accounts   | As an operator, I want two bank transactions of equal and opposite amount, in two of my accounts in the same Budget and currency, dated at most 5 days apart (a number I can change), and recognised as a card payment or a bank transfer, to be detected as one transfer so that it can arrive as one linked transfer. | High | Open |
| FR-047 | Upload a Transfer as One Linked Transfer | As an operator, I want a detected transfer to be uploaded as one transfer leg that the Budget App links to the other account, never as two separate transactions, so that I do not have to re-link it in the Budget App. | High | Open |
| FR-048 | Never Pair Across Budgets or Currencies | As an operator, I want movements between Budgets or between currencies never to be treated as transfers so that each side stays an ordinary transaction and no currency is converted. | High | Open |
| FR-049 | Review Guessed Transfers                | As an operator, I want a transfer that Slussen cannot pair unambiguously to be flagged as guessed, with the number of guessed transfers shown per Budget, so that I confirm or correct each guess before upload. | High | Open |
| FR-050 | Correct a Transfer                      | As an operator, I want to confirm a transfer, split it into ordinary transactions, hold it back, or choose the other account it belongs to, and optionally remember that account for future transfers of this account, so that every transfer lands where I intend. | High | Open |
| FR-051 | Transfer With One Side Missing          | As an operator, I want a transfer of which only one side has arrived to be shown with the expected other side and uploaded as a linked transfer whose counterpart stays uncleared, and to become an ordinary transaction when its other side has not arrived within 6 days (a number I can change), so that a transfer is not held back indefinitely. | High | Open |
| FR-052 | Settle the Transfer Counterpart         | As an operator, I want the counterpart that the Budget App created for a transfer Slussen uploaded to be marked cleared, and the arriving bank transaction for that side not to be uploaded again, when the other side's bank transaction arrives, so that the transfer ends fully cleared without a duplicate. | High | Open |
| FR-053 | Clear the Counterpart When Both Sides Are Present | As an operator, I want a transfer whose both sides were fetched to land with its counterpart marked cleared at upload so that the transfer is complete on both accounts at once. | Medium | Open |
| FR-054 | Review a Changed Transfer Counterpart   | As an operator, I want an arriving bank transaction whose transfer counterpart was changed or unlinked in the Budget App to be shown to me for review instead of being suppressed so that no side of a transfer is silently lost. | High | Open |
| FR-055 | Only Clear Own Counterparts             | As an operator, I want marking a transfer counterpart as cleared to be the only change Slussen ever makes to an existing Budget App transaction, and only for a counterpart created by a transfer Slussen uploaded, so that the Budget App otherwise stays exactly as I keep it. | High | Open |
| FR-056 | Map Each Bank Account to One Budget Account | As an operator, I want each bank account to be mapped to exactly one Budget and Budget Account, as set in my build configuration, so that each bank account's transactions land in the right place. | High | Open |
| FR-057 | Lock a Mapping After First Upload       | As an operator, I want the mapping of a bank account to be locked once a transaction was uploaded through it, with the reason shown wherever a change is refused, so that already-uploaded transactions are never created again in another account. | High | Open |
| FR-058 | Never Guess an Account                  | As an operator, I want Slussen to use a bank account's transactions only when it identifies the account with certainty, to ask me to confirm when it can only propose a likely account, and to stop when two accounts are possible or two mappings would point to the same bank account, so that one account's transactions are never sent to another account. | High | Open |
| FR-059 | Retire and Restore an Account           | As an operator, I want to retire an account so that it is no longer fetched, compared, matched or uploaded, and to restore it later with its identity and history intact, so that I can pause an account without losing anything. | Medium | Open |
| FR-060 | Separate Budgets                        | As an operator, I want each Budget, with its own currency, to be shown as its own workspace with only its own sources, accounts, transactions and number of transactions to upload so that I never mix up Budgets. | Medium | Open |
| FR-061 | Compare Balances                        | As an operator, I want each account's bank balance shown next to its balance in the Budget App, with the difference, in one place so that I can reconcile them at a glance. | High | Open |
| FR-062 | Hide Outdated Balance Differences       | As an operator, I want the balance difference of an account to be hidden and marked as outdated when its bank balance is older than 36 hours (a number I can change) so that I never reconcile against an old balance. | Medium | Open |
| FR-063 | Show Source Health and Freshness        | As an operator, I want each source and account to show the outcome of its last fetch and, separately, how old its data is so that I can see at a glance whether the Budget App is up to date with each source. | High | Open |
| FR-064 | Show the Blocked Reason and Its Remedy  | As an operator, I want every account or source that cannot be fetched or uploaded to show the reason (for example missing consent, unrecognised account, waiting for the provider, daily limit reached, configuration error) together with the action that removes it so that I know what to do. | High | Open |
| FR-065 | View Recent Fetch Outcomes              | As an operator, I want to see the 60 most recent fetch attempts with source, time and outcome so that I can tell when each source last brought data back. | Low | Open |
| FR-066 | Record the Decision Journal             | As an operator, I want Slussen to record what it fetched, the status it gave each transaction, every decision I made together with what Slussen had proposed, every upload plan and upload, every account mapping change, and what later happened in the Budget App to each transaction Slussen sent, so that I can measure afterwards how often Slussen was right. | Medium | Open |
| FR-067 | Control the Decision Journal            | As an operator, I want to switch the decision journal on and off (on by default), to set its size limit between 10 and 500 MB (50 MB by default), to be warned when it reaches 80% of the limit, and to clear it, so that it never fills my phone. | Low | Open |
| FR-068 | Export the Decision Journal             | As an operator, I want to export the decision journal to a file I choose, together with the Budget App's current transactions for my Budgets (or Slussen's stored copy of them when the Budget App cannot be reached, stated in the file), optionally with payee and memo text replaced by codes, so that I can review Slussen's accuracy outside the app. | Medium | Open |
| FR-069 | Switch On Detailed Logging              | As an operator, I want to switch on detailed logging that includes transaction data and account numbers, and switch it off again, so that I can troubleshoot a problem on my own phone. | Low | Open |
| FR-070 | Configuration Templates                 | As an adopting developer, I want a configuration template for each Data Provider and the Budget App in this build that shows what to fill in and where to get it so that I can configure my own build without reading the code. | High | Open |
| FR-071 | Configure Own Accounts at Build Time    | As an adopting developer, I want to set my own accounts, Budgets, account mappings and service credentials in configuration kept outside the repository and have them included when I build so that my build works for my household without changing the repository. | High | Open |
| FR-072 | Add a Data Provider or File Format      | As an adopting developer, I want to add a Data Provider or file format, stating whether it gives each transaction a stable reference, so that I can bring in a bank this build does not reach. | Medium | Open |
| FR-073 | Replace the Budget App                  | As an adopting developer, I want to connect Slussen to a different Budget App by replacing only the part that talks to the Budget App so that I can use Slussen with the Budget App my household uses. | Medium | Open |

## Non-Functional Requirements

| ID      | Title                              | Requirement | Category | Priority | Status |
|---------|------------------------------------|-------------|----------|----------|--------|
| NFR-001 | Zero Duplicates                    | Across retry, timeout, lost connection, crash, reinstall and re-mapping test scenarios, Slussen creates 0 duplicate transactions in the Budget App. | Availability | High | Open |
| NFR-002 | Zero Silent Drops                  | Across the same test scenarios, 0 bank transactions that Slussen fetched or imported disappear without being uploaded or shown to the operator with a status. | Availability | High | Open |
| NFR-003 | Upload Plan Lifetime               | An upload plan expires 10 minutes after it was prepared; confirming an expired plan writes 0 transactions. | Security | High | Open |
| NFR-004 | Crash-Free Network Loss            | Losing the network at any point of a fetch, a Budget App read or an upload causes 0 app crashes and 0 transactions shown as written that were not confirmed by the Budget App. | Availability | High | Open |
| NFR-005 | Corrupt Stored Data                | When a stored file cannot be read, Slussen keeps the unreadable original unchanged, starts from its last good or default content, shows a notice, and does not crash, in 100% of tested cases. | Availability | High | Open |
| NFR-006 | Journal Never Affects Decisions    | Deleting, switching off, filling or corrupting the decision journal changes 0 transaction statuses, upload plans or uploads, and a journal write failure fails or delays 0 operator actions. | Availability | High | Open |
| NFR-007 | Default Logs Without Personal Data | With detailed logging off, device logs contain 0 transaction amounts, payees, memos or account numbers. | Security | High | Open |
| NFR-008 | Never Log Credentials              | In every logging mode, device logs contain 0 credentials, bank consent data, authentication codes or one-time values. | Security | High | Open |
| NFR-009 | Backups Exclude Logs and Bank Consents | Device backups and device-to-device transfers include 0 logs, 0 bank consent data and 0 consent requests in progress. | Security | High | Open |
| NFR-010 | Backups Include the Sent Record    | Device backups include the sent record, the account identities and mappings, and the review and transfer decisions, so that a restore after reinstall loses 0 of them. | Availability | High | Open |
| NFR-011 | Journal Excluded From Backups      | The decision journal is included in 0 device backups; it leaves the device only through a journal export the operator starts. | Security | Medium | Open |
| NFR-012 | Journal Without Secrets            | The decision journal and its exports contain 0 credentials, bank consent data, account numbers, bank account identifiers or provider error texts. | Security | High | Open |
| NFR-013 | One-Time Consent Request           | Each bank consent request is valid for at most 15 minutes, is accepted at most once, and is rejected if it is not the most recent request for that bank. | Security | High | Open |
| NFR-014 | Core Rules Independent of Providers | Adding a Data Provider or file format changes 0 files of the rules that compare, review and decide. | Maintainability | Medium | Open |
| NFR-015 | Budget App Behaviour Isolated      | Every rule that depends on one Budget App's behaviour lives in that Budget App's own part; replacing the Budget App changes 0 files of the rules that fetch, compare, review and decide. | Maintainability | Medium | Open |
| NFR-016 | Request Timeout                    | Every request to a Data Provider or to the Budget App gives up after at most 30 seconds and is then treated as a failed or unknown-outcome request. | Performance | Medium | Open |

## Constraints

| ID    | Title                                 | Constraint | Category | Source | Priority | Status |
|-------|---------------------------------------|------------|----------|--------|----------|--------|
| C-001 | Android Phone                         | Slussen runs natively on the operator's Android phone, and everything it stores stays on that device. | Technical | | High | Open |
| C-002 | No Server Component                   | Slussen has no server or hosted component, no remote access and no synchronisation between devices. | Technical | | High | Open |
| C-003 | Private Build per Operator            | Each installation is built for one operator with that operator's build configuration and is installed directly on the phone; a built app is never published, because credentials can be extracted from it. | Business | | High | Open |
| C-004 | Rotate Exposed Credentials            | If a built app leaves the operator's control, every service credential included in it is revoked and replaced before Slussen is used again. | Operational | | High | Open |
| C-005 | Public Repository Without Personal Data | The repository, including its specifications, tests and fixtures, contains no real account names, account numbers, Budget identifiers, transactions or credentials. | Business | | High | Open |
| C-006 | Unattended Access Limit               | A bank allows an application without the account holder present at most four accesses per account in 24 hours, counted separately for transactions and balances. | Regulatory | PSD2 RTS, Commission Delegated Regulation (EU) 2018/389 Art. 36(5)(b) | High | Open |
| C-007 | Consent Renewal by the Account Holder | A bank consent expires (about 90 days after it was granted) and can be renewed only by the account holder through the bank's Strong Customer Authentication. | Regulatory | PSD2 RTS, Commission Delegated Regulation (EU) 2018/389 Art. 10 | High | Open |
| C-008 | External Services in This Build       | The Data Providers in this build are SimpleFIN and Enable Banking, and the Budget App is YNAB through its public interface; their rules are fixed and Slussen works within them. | Technical | | High | Open |
| C-009 | YNAB Matching Rules                   | YNAB matches an import to a typed entry in the same account with the same amount within 10 days before or after; it never matches two imports to each other; it keeps an import identifier locked, so that it cannot be used again, even after the transaction is deleted. | Technical | | High | Open |
| C-010 | One Budget App and One File Format    | This build supports one Budget App at a time (YNAB) and one transaction file format; other Budget Apps, Data Providers and file formats are added later without changing the core rules. | Technical | | Medium | Open |
| C-011 | Proof Against the Real Budget App     | Every guarantee that depends on YNAB's behaviour (matching, deletion, merging, transfers) is shown by a test against a real, throwaway YNAB budget before uploads that rely on it are trusted. | Operational | | High | Open |
| C-012 | One Import Path per Account           | Every account that a source exposes is imported only through Slussen, never also by hand or by a second importer; an account no source exposes stays a manually kept account. | Operational | | High | Open |
| C-013 | Specification First                   | Slussen is developed with the AI Unified Process: the specification in `docs/` is the source of truth, and the predecessor app is evidence of intent, not a template. | Business | | High | Open |
