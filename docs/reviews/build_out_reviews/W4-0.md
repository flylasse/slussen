# Review of phase W4-0 (d0a9aaf), the specification for Wave 4 (Uploads)

Independent reviewer, read-only, a fresh context (Opus, as the writer: the plan's §5 row 3). The reviewer read YNAB's public documentation and OpenAPI description itself. **A second review by the strongest model is owed before phases C3, C5a and C5b build on this specification** (after the weekly reset; the plan's §0).

**Confirmed in the documentation:** one endpoint creates a single transaction or a list, answering 201, 400 or 409; 409 means the same account and the same `import_id`, and a list names its `duplicate_import_ids`; `import_id` is unique for each account; a transaction is unapproved by default; a transfer is made through the other account's `transfer_payee_id`; YNAB matches an import to a user-entered transaction of the same amount within 10 days; the lengths of `import_id`, payee and memo; no future dates, all dates in UTC; 200 requests an hour, answered with 429; amounts in milliunits; deleted transactions are included only in delta requests; the update by `id` cannot create a transaction. **Not documented:** that a deleted transaction keeps its `import_id` refused; that a refused list writes nothing; what YNAB creates on the other side of a transfer; how long a `server_knowledge` stays usable; that deleting one side of a transfer deletes the other; that a closed account refuses a new transaction; an age limit on old dates; that an update of `cleared` changes nothing else.

**Sound:** a write that succeeded and is not visible yet is retried under the same Import Identifier to the same Budget Account, where the documented refusal makes it Already Present; a process that ends at any step leaves Not Yet Known, Unknown at the next start, and nothing is resent before a plan is confirmed; the resend one by one after a refused list is safe even if the list stored some items, and is bounded at one request for each item; a Re-upload is used up by its send; a Transfer is frozen once a Transfer Leg is uploaded; a merge the reader cannot recognise is read as a deletion; an Import Identifier held only in another Budget Account is Needs Review; admission, a decision replacing an open plan, the deferred Scheduled Fetch; the window between the check at confirmation and the write is seconds, in which only another import path could duplicate; shortening is part of no identifier; the rules owed (W4-01 to W4-12) and the answers are each in place; no column is missing at `slussen.db` version 6; the evidence needs no agent to hold a token.

## To correct in this phase, with the orchestrator's decisions

1. **PLAUSIBLE, high. A send whose outcome is unknown can be sent again into another Budget, and then end as a second write.** An Upload Plan has one Budget (S-B-68), but the retry table sends an Unknown send to the Budget Account recorded in it "also when the Operator has moved the Account Mapping since", and a move across Budgets is allowed. Sequence: a send to a Budget Account of one Budget loses its answer; the Operator moves the Bank Account's mapping to another Budget; the first Budget has no mapped Bank Account left and is never read again, so the unknown is never settled; the next plan, of the other Budget, holds the retry to an account outside it; YNAB refuses each, which is recorded as Rejected; Rejected follows the present mapping, and the next plan sends the same Import Identifier to the new Budget Account, where nothing refuses it. If the first write did arrive, the transaction is in the Budget App twice. **Decision:** a send that is not settled (Not Yet Known or Unknown) is retried only to its own Budget Account in a plan of that Budget Account's Budget; in a plan of any other Budget it gives no item, and the Bank Transaction stays Outcome Unknown and is sent nowhere else; a Budget is read as long as an unsettled Sent Record names one of its Budget Accounts, mapped or not; a refusal because the account is not in the plan's Budget is never recorded as Rejected. UC-009 A8 step 3, which tells the Operator such sends are "never sent again", is brought in line.
2. **PLAUSIBLE / CONFIRMED gap. A new installation, Start Over and an old restore rest on facts that are not documented.** A transaction an earlier installation sent and the Operator then deleted in the Budget App is invisible to a first read, so its Bank Transaction is New and sent again; only the undocumented refusal of a deleted `import_id` stops it, and C-009 still states that refusal as a fact. A restore rests on an old `server_knowledge` still being answered with the deletions, for which E-10 has no test. **Decision:** C-009 says what is documented and what E-10 must prove; E-10 gets the case of a stale cursor; after a restore, a start from the last good copy or a new installation the stored cursor is not trusted (the read period is read anew), which the specification states if it does not already; what happens when the test of the deleted `import_id` fails is written as a rule (such a Bank Transaction comes back as an unapproved transaction the Operator deleted before: no duplicate, and told in First Upload Matching's text) and put to the operator (G-44).
3. **PLAUSIBLE. The lock of S-B-71 and the Needs Review of Q-10 see only Transfer Counterparts that are recorded**, and a row exists only after the read that follows a write, or after a Comparison settled the send: a Lonely Transfer written while that read or Comparison failed has none; the other Bank Account's mapping can then be moved without confirmation, and its arriving side is New and uploaded beside the counterpart. **Decision:** a Sent Record sent as a transfer and not Rejected counts for the side its Transfer names, whether or not the Transfer Counterpart is recorded yet (UC-009 BR-003, ADR-002 O-13, UC-005 BR-010).
4. **CONFIRMED. ADR-007 §6 step 4 is ambiguous** on what is stored when the check at confirmation finds no change and when it finds one: two sentences.
5. **CONFIRMED against the documentation. Every 403 is mapped to refused credentials**, while the documented kinds for a lapsed subscription, an expired trial, a data limit and an unconfirmed address are not: only an answer that means the token is not accepted is refused credentials; the others are the Budget App's refusal with their reason.
6. **PLAUSIBLE, low. Q-10's Needs Review holds only within the Budget App's Matching Date Window** of an unsettled Transfer Counterpart; a side booked later is New beside a counterpart never settled. **Decision:** at any date while the counterpart is not settled.
7. **CONFIRMED, minor.** UC-003 A6's trigger still names only the two unsettled outcomes; a bare word in the plan's row S-B-62; `upload-outcome.html` lacks the state of an outcome read back after a restart (S-B-74); an item for which no request left is recorded and shown as Unknown: the text for Unknown is true for both cases (whether it reached the Budget App is not known or it was not sent; it is checked at the next read and sent nowhere else before).
8. **PLAUSIBLE. Moving the working reads to the documented `/plans` paths is not needed** and changes code the operator uses today; the older paths still answer. **Decision:** the writer uses the paths the reads use; the move is put to the operator with a live test that the two name the same thing (G-44). A single transaction's answer is checked for its `import_id` as a list's is.

## For the question list (G-44), only the operator or a live test can answer

- Whether YNAB matches a linked transfer onto a hand-typed one or makes a second pair (Q-04; E-10): no rule of Slussen stops a second pair; it rests on the operator typing nothing ahead.
- If the other side YNAB creates for a transfer arrives approved: what Slussen should do.
- If a deleted `import_id` can be used again: what replaces that protection after a new installation and Start Over.
- An amount finer than the Budget's currency allows.
- From what age YNAB refuses an old date.
- The move from the `/budgets` paths to the documented `/plans` paths.
