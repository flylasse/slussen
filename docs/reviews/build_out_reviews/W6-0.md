# Review of phase W6-0 (22a3e8f), the specification for Wave 6 (Bank Consent and Enable Banking)

Independent reviewer, read-only, a fresh context (Opus, as the writer: the plan's §5 row 3). The reviewer fetched Enable Banking's public documentation itself (the OpenAPI description, the FAQ, the Control Panel page) and checked the facts the new rules rest on.

**Confirmed in the documentation:** an account's identifier of a session changes at every new authorisation and may be missing, and `identification_hash` is the value for matching accounts between sessions (the specification's reference that lasts; when it changes the Operator confirms, never a guess); a transaction's required and optional fields and its statuses; balances carry no credit or debit indicator; paging by a continuation key, where an empty page with a key must be followed; `access.valid_until` is required, bounded by the Bank's maximum, and the session lasts as asked; at least one header of the Operator's presence lifts a Bank's background limits, a Bank's required headers go all or none; every error code named in ADR-001 §4.1.1 exists; ending a session closes the Bank's consent only "if possible". **Not documented:** whether a return address with a custom scheme is accepted.

**No findings** on: the state value (made by the core, only its digest stored, used once, read by `stateOf`; a pasted answer checked the same way; debug and release cannot take each other's answer; nothing sensitive logged); each flow of UC-007 has one outcome; ADR-007 §2 and §3; `device.db` version 2 adds tables only and `slussen.db` stays at version 6; booked transactions only, the booking date only, a missing field gives an Unreadable Transaction; the balance's choice fails safe; an incomplete sequence of pages stores nothing of that Bank Account; the memo's form is exact; the count builds on Wave 5's Provider Requests; K-04; Q-05; nothing settled earlier is settled again differently.

## To correct in this phase, with the orchestrator's decisions

1. **CONFIRMED. The Fetch Cooldown never starts for a Data Provider that needs a Bank Consent.** UC-001 BR-006 and the code decide whether a Fetch "delivered a Bank Account" from the Offered Bank Accounts it kept, and by the new rule such a Fetch keeps none: every Fetch the Operator starts would contact the Bank. **Decision:** BR-006 says, for such a Data Provider, that a Fetch delivered when it read at least one Bank Account.
2. **CONFIRMED. The Operator's own Fetch could be refused by Slussen, and the requirement was not changed.** At a Bank that requires the device's address as a header of presence, no such header can be sent (all or none), so every request counts as unattended, also a Fetch the Operator started; by the new A13 he would be refused after four reads in 24 hours, with a text that does not say why, and FR-079 covers only the Scheduled Fetch. **Decision:** Slussen counts truthfully (a request sent without a header of presence is counted as an Unattended Access whoever started it), and its own limit refuses only a Scheduled Fetch (FR-079 unchanged). A Fetch the Operator starts is never refused by Slussen's count: Slussen says before it that this Bank counts it as unattended and how many are used, and the Bank's own answer decides (a refusal is a Back-off of that Bank, UC-001 A5).
3. **CONFIRMED. "The Operator's decision of 2026-11-26"** that Slussen never asks a third party for the device's address is recorded nowhere. **Decision:** it is the orchestrator's choice, not the operator's: worded as such, and to the question list (G-39).
4. **PLAUSIBLE. Counting each page as an access can make a Bank Account unreadable for good**, and neither C-006, FR-079 ("reads") nor the documentation supports it. **Decision:** one read of a Bank Account's transactions in one Fetch is one access, however many pages, and one read of its balance is one; the Bank's own refusal is handled as A5. To the question list (G-39).
5. **PLAUSIBLE. Nothing stops a continuation that never ends.** **Decision:** a continuation key that was already used in the same read ends it as incomplete; the Request Limit bounds the rest.
6. **PLAUSIBLE. A minus sign with the debit indicator is a guess** (a doubly signed outflow, or a reversal). **Decision:** an amount with a minus sign is an unreadable amount, whatever the indicator (UC-001 BR-016).
7. **CONFIRMED. A consent the Bank refused is shown two ways** (UC-001 A9 step 3 "missing consent"; the entity model "shown as expired with that time"). **Decision:** one: an expired Bank Consent, with the time and that the Bank refused it; renewing is the remedy.
8. **CONFIRMED. Nothing says when the `BANK` row of a newly chosen Bank is created**, and one created at the start would be left by a refused or abandoned attempt and offered later. **Decision:** a Consent Request holds the Bank's reference; the `BANK` row is created when the Bank Consent is granted.
9. **CONFIRMED. The mockup's new states show the Bank's name without its country**, the rule with it. The mockup follows the rule.
10. **PLAUSIBLE. If the Data Provider does not accept the application's own address as a return address, no path completes a consent**: the address cannot be changed, and pasting back does not help when the browser never shows the address. **Decision:** the return address registered at the Data Provider is stated with that Data Provider's credentials (UC-014; a field the plug-in declares, empty meaning the application's own address `<application id>://consent`). With an https address of the Operator's choosing, the browser ends on that page with the answer in its address, and the Operator pastes the address back (UC-007 BR-011). No new Operator Setting. To the question list (G-39).
11. **Smaller.** A renewal asks the Data Provider to end the earlier session after the new Bank Consent is stored (a failure of that request does not undo the renewal, and is said); Start Over says before the Operator confirms that a Bank Consent it cannot end stays at the Bank until it expires; an account delivered without the identifier of its session is not delivered as a Bank Account that can be read; "card account" in the plan's row.

## For the question list (G-39), only the operator can answer

- May his own Fetches at a Bank that requires the device's address count against that Bank's four a day; should the Fetch Schedule leave such a Bank out. Slussen asks no third party for the device's address.
- One Unattended Access: a read of a Bank Account, as decided here, or each page.
- Whether Enable Banking's Control Panel accepts `slussen.app://consent`; if not, the https address he wants to register.
- A credit card Bank Account read through Enable Banking gets no Account Balance (a balance carries no sign): acceptable?
