# Review of phase W2-1 (2134fa9..d4b9e5b), `slussen.db` version 6

Independent reviewer, read-only, another model than the builder. It also replayed `MIGRATION_5_6` on SQLite in a script outside the repository, with `legacy_alter_table` off and on: in both runs the Transfer Leg still pointed at its Transfer, `sqlite_sequence` was kept, `foreign_key_check` was empty, removing a referenced Transfer was refused, and the next id followed on.

**No serious finding.**

1. **`MIGRATION_5_6` (`SlussenMigrations.kt:146-226`): no findings.** It follows SQLite's documented order: create `_new_transfer`, copy all columns by name with `id` kept, carry `sqlite_sequence` over, drop the old table, rename, recreate both indices, then the foreign key check. Nothing references `_new_transfer`, so the rename needs no rewrite of references on any SQLite version (API 26 included); `bank_transaction` is not touched. Foreign keys are off during the Migration (Room turns them on at open). A violation makes the Migration throw and roll back to version 5; it cannot be reached in practice, since the start's database check runs the full `foreign_key_check` on the version 5 file before Room opens it. The table and index SQL match `6.json` statement by statement; `1.json` to `5.json` are unchanged and version 5's digest is the pinned one.
2. **The seven new tables against the entity model: no findings.** Names, types, optionality, Unique constraints, foreign keys and `Values:` match. Optional references made real foreign keys follow version 5's precedent. PLAUSIBLE, low, could force a version 7: the header of `upload_plan_item` holds one `change_cursor` and no `budget_id`, which fits one Budget per Upload Plan (`UPLOAD_PLAN.budget_id`); ADR-007 §6 step 4 says "for each Budget of the plan", so if a plan ever spans Budgets a column is needed. To settle in Wave 4's specification.
3. **`state_version`: no missed raise, and none outside its change's transaction.** The operations that do not raise it feed nothing an Upload Plan is prepared from. **To fix (low, CONFIRMED):** the fake diverges from Room: `InMemoryStores.kt:184-197` raises for any existing Data Provider, `MainDaos.kt:80` only when the update stores something. Case: a Data Provider that publishes its Request Limit, and `storeRequestLimit` called: the fake's version rises, the device's does not, so a core test could see a raise the phone never makes.
4. **Tests: no findings.** The JVM migration tests would catch a lost row, a changed value or a renumbered id, a lost reference, a wrong default and a reset sequence. `EntityModelSchemaTest` does what its names say (its foreign key check is one-way: it would not flag a foreign key the model lacks). Both instrumented tests' set-ups can produce what they assert. The builder's claim of eight planted faults was not checked.
5. **`:core` and `:testing`: no behaviour change.**
