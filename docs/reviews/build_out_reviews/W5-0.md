## To correct in this phase, with the orchestrator's decisions

1. **CONFIRMED. The memo leaves a choice, and it feeds a permanent reference.** ADR-001 §4.3.1 says "the one present alone" for a line with a `Symbol` and no description: `EXMPX` or `(EXMPX)`; no test vector covers it. **Decision:** the description alone is the description; the symbol alone is the symbol in parentheses; stated exactly, with a test vector for each.
2. **CONFIRMED. What only the process holds is lost after a Scheduled Fetch in the background**, and UC-001 A21 still says its currency notice is shown, against the new BR-013. G-20 (the notice of `device.db` or `journal.db` set aside) and G-01 (a failed read of a Budget) are of the same kind. **Decision:** no column is added. BR-013 names what is not shown once that process has ended (the notices held only by the process) and what the Operator still sees from stored state; A21 gets its exception for a Scheduled Fetch; G-20 and G-01 stay in the question list.
3. **CONFIRMED. A deferred Scheduled Fetch started at a start of Slussen contradicts UC-001 BR-001 and UC-008 BR-001** (opening Slussen never contacts a Source), and when the stored flag is cleared was not said. **Decision:** opening Slussen never starts it. A deferred Scheduled Fetch starts when the mode returns to Normal in the running process; otherwise the next run of the schedule is the one that fetches. The flag is cleared in the transaction that records the start of a Scheduled Fetch, so that an ended process neither loses the deferral nor runs it twice. ADR-007 §8 follows.
4. **CONFIRMED. The glossary still says** that two transactions that would get the same reference have no Stable Reference, against UC-002 BR-003 step 3. Corrected.
5. **CONFIRMED. The permission to see the network's state rests on behaviour no use case states.** **Decision:** UC-001 BR-013 says that a Scheduled Fetch starts only while the device has a network connection and otherwise waits for one.
6. **PLAUSIBLE. Every line taken as booked is a guess** the description neither supports nor denies. **Decision:** it stays (the description names no pending line), and goes to the question list (G-35) for the operator: whether his export ever holds a pending line.
7. **PLAUSIBLE. "Never retried" and a device that starts an interrupted run again.** **Decision:** BR-005 concerns a Fetch that failed; BR-013 says that a run the device interrupted may be started again by the device, that Slussen itself starts none, and that the Request Limit bounds it.
8. **CONFIRMED. A Fetch of one Budget has no entry, and G-05 waited for one.** No entry is added (the specification has none); G-05 stays, with a note.
9. **CONFIRMED. The mockup `budget.html#fetch-failed-scheduled` says the next falls due after the last**, BR-013 counts from when the Fetch Schedule was set. The mockup follows BR-013 and shows an approximate time.
10. **The format's rules that only reject.** **Decision, to spare a first import rejected for a detail the description cannot settle, none of which changes a reference:** the byte order mark may be present or absent; lines end with LF or CRLF, one kind in a file; the text after the transaction lines is not read, and only its presence is required (an empty line, then text whose last line begins with `Date downloaded`), so that a file cut short is still rejected. The other rules stay (`Type`, the order of `Run Date`, the number's form).
11. **Smaller.** Step 2 of UC-002 BR-003 applies to lines with a Derived reference only (a line with a Supplied reference that no stored Bank Transaction holds is new); the count of a rejected file is 0; a wrong citation (UC-014 BR-007); `overview.html#notification-ask` follows BR-014's wording; "a health savings account" without the bare word (AGENTS.md §2).
