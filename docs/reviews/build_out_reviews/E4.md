# Review of phase E4 (be00bf4..270a6df), the consent screens and the return to Slussen

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3).

**Sound:** the manifest's filter (the application's own id as the scheme, so debug and release take only their own answers; the device permissions unchanged; the `<queries>` element as narrow as it can be); which intent is an answer (the view action only, the exact address, extras ignored); the time of arrival taken when the intent arrives, and a time after now only ever makes an answer later; answers handed in one at a time, a second delivery dropped only when the core says it was already answered; only the address the plug-in returned is ever opened, and it must be https; no path reaches the plug-in's unbuilt Fetch once a Bank Consent is stored; the core changed only by adding; nothing at a start contacts a Data Provider; Renew offered only where it should be; the texts for "may have been granted", an end the Bank did not confirm, an earlier consent that may stay at the Bank, Offered Bank Accounts not kept, and a refused return address say what the core reported.

## To fix in this phase, with the orchestrator's decisions

1. **CONFIRMED. An intent from anyone changes what the Operator is told about his real consent** (`ConsentAnswers.kt:114-126`, `ConsentTexts.kt:163-169`, `ConsentBanner.kt:40-50`). Any app or page can open the return address. An address with no state is refused by the core without contacting anyone, which is right; but the app then pins that refusal on the one Bank that is waiting ("Result not accepted · that Bank · Start again"), puts it in place of the waiting banner and its Cancel, or in place of a "granted" the Operator has not seen yet; and "Start again" replaces his real, still waiting, Consent Request. **Decision:** an address that matches no Consent Request is no result of any Bank: it replaces nothing and removes nothing; at most one neutral line says that an address was opened that answers no Consent Request. While one such address is being checked, further ones are dropped.
2. **CONFIRMED. The main screen's activity became `singleTask`**, so that any intent to the return address, real or not, closes whatever is open above Slussen (a document dialog of an import or an export), and its handling rests on the activity's saved state. **Decision:** the return address is received by a small activity of its own, without a screen, that hands the address to the process-wide holder of answers, brings Slussen forward as it is and ends; the main activity keeps the launch mode it had before this phase. If that cannot be built without a new risk, the builder says why and keeps the present way.
3. **CONFIRMED. A refusal of the credentials is noted at the optional return address whenever it is filled in** (`ServicePageViewModel.kt:54-56, 596`), also when another field was wrong. Only the plug-in's own check of that field notes it there; a refusal by the Data Provider is said as a refusal of the credentials.
4. **CONFIRMED. A browser that fails to open after the start was sent is told as "nothing was sent"** (`BankConsentsViewModel.kt:357-361`), and a failure of the abandoning that follows is thrown away. The text says what happened; when the request could not be abandoned it stays shown as waiting, with its paste field and Cancel.
5. **PLAUSIBLE. After the process ended while the Operator was at the Bank, nothing says how it went**: a Consent Request whose lifetime ended meanwhile, and one whose answer was consumed without a Bank Consent stored. At a start both are read from stored data and said once: not granted, the time for the answer ended; or, may have been granted, start again.
6. **PLAUSIBLE. "Result not handed in" asks the Operator to paste an address his browser never showed.** The text says that the answer is lost and to start again; pasting is offered only where an address can have been shown (a registered return address other than the application's own).
7. **Smaller.** The paste field takes a one-time value: no auto-correction or learning by the keyboard. A test that the banner's Cancel abandons the right request, and tests for item 1.

## Decided in the specification (proposed as S-B-54): the mockup follows the use case

`consent.html`: an expired Bank Consent's variant "the Bank refused it" with its date (UC-008 BR-006); no "until" time before a Consent Request has started; the Data Provider's refusal split into "try again later" (A3) and "start again" (A4); the registered return address named where none is granted yet (S-B-51). `connections.html`: Renew without credentials, with its reason (UC-014 BR-005).

## For the end checklist (a device and a real Bank)

The return while Slussen runs; the process ended while at the Bank; a start of Slussen from the address; rotation and recents after a return (no second hand-in); two browsers, and a Bank's own app that returns through another browser; two taps on the return link; a sign-in cancelled at the Bank; a lifetime that ends in the background; a document dialog open when the return arrives; a bare return address sent by `adb` while a request waits.
