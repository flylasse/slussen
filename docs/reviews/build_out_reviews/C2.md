# Review of phase C2 (c940fe2..8a1862f), the YNAB writer and the read of one transaction

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3). The reviewer compared each request and answer with YNAB's OpenAPI description and its table of errors, and read the HTTP library's own retry code. **A second review by the strongest model is owed with W4-0's, before phases C5a and C5b call this writer** (the plan's §0).

**No finding** that writes what was not handed or stores a transaction twice. Compared with the documentation and matching: the create (one list, or one transaction for a resend; every field, the amount as exact milliunits and refused before sending when it cannot be exact, `approved` false, the Import Identifier as handed, a transfer through the other account's transfer payee, no category, flag or split); what is read of its answer; the update by `id`, which cannot create; the read of one transaction; the read of the accounts; each error of the documentation's table. Sound: the gate before every request; no redirect followed; the library's resend on a failed connection switched off, proven by counting requests at the server; the resend one by one starts only on a list refused as a whole, never on an unreadable answer, a request to wait, a failing service, a timeout or a lost connection, which give Unknown for every item; a list's own refusal never gives Rejected directly, and an item the refused list did store is then Already Present; each answer gives each item exactly one outcome as ADR-001 §4.2.5 states; a cancellation at any point keeps the outcomes already answered; no log line or `toString` of an item or an outcome shows a token or a value; no gate task runs a live test, the values are never printed, every writing live test checks the Budget's name first, and the one test against the real Budget sends a single read.

## To fix in this phase, with the orchestrator's decisions

1. **CONFIRMED. The HTTP library sends a write a second time, past the gate, when the answer is a service-unavailable status that says to retry at once** (`Http.kt:32-39`): that follow-up does not depend on the setting that was switched off, and YNAB documents that status for a request that timed out, so the first write may already be stored. The second is then answered with every item as a duplicate and reported Already Present: no transaction twice, but a request the gate never admitted (ADR-001 §4.0), and the same gap in the clients of the two Data Provider modules. **Decision:** no status makes the library send again, in all three modules' clients, each proven by a test that counts requests at a local server.
2. **PLAUSIBLE. "An account that is not in the Budget named is Unknown, never Rejected" rests on an answer YNAB does not document** (the documentation lists a create's refusals without that case): if YNAB answers it as a validation error, the item is recorded Rejected, which is the path to a second write in another Budget that W4-0's review closed in the specification. **Decision:** the writer does not rest on YNAB's answer: an item whose Budget Account is not among the accounts it read for that Budget in the same call is not sent and is Unknown; E-10 gets the case (what YNAB answers to an account of another Budget).
3. **CONFIRMED. The scripted writer of `:testing` behaves differently from the contract the real writer passes** (a cancellation while the gate decides; one question to the gate for a call where the real one asks before every request; outcomes already answered lost on a cancellation; no script for a clearing whose answer was lost): the tests of phases C5a and C5b would rest on it. It is run against the same contract test and passes it, and it can script what the real one can do.
4. **PLAUSIBLE. Several live tests can report a false fact**: two assume opposite things about a match awaiting approval, and one's wait can already hold before the Operator approves; amounts are reused across runs within the window they read, so a second run within weeks fails or miscounts; one can only print, not fail. Each proves its fact on a first and on a repeated run, or says plainly that it only shows what YNAB does for the operator to read.
5. **PLAUSIBLE, low. A clearing answered without a list of transactions is told as not cleared**, where the documentation allows a single one: both forms are read.
6. **PLAUSIBLE, low. A refusal of the Budget App that is not of the token (a lapsed subscription, an ended trial, a data limit, an unconfirmed address) is told as a service to try again later**, without its reason, on the reads and the check of credentials. **Decision:** a failure kind of its own in the contract, with the reason from a closed set, and its text in the app.
7. **Low.** The data classes of a read (a transaction, a transfer's link, a merged state, a Budget, a Budget Account) still print payees, memos and references; neither test of planted values checks them.
8. **Low.** The writer cuts payee and memo by a rule of its own, and the core's does not exist yet: one rule in one place, as ADR-001 §4.2.4 assigns it; where the other side receives a text that is too long it does not cut silently.

## Owed to phases C5a and C5b (the plan's W4-13)

Call the writer so that a cancellation cannot throw its outcomes away, and record them at once, uncancellable; hand it only Budget Accounts of the plan's own Budget; never store or journal a rejection's reason from the Budget App, and bound it on screen; never plan a clearing for a counterpart that is reconciled; take the permit and the rule of one Budget Account for each call in the admitted writer, since the raw one checks neither; expect up to two requests and one for each item for a Budget Account; a refusal of the Budget App's own kind does not stop a resend.
