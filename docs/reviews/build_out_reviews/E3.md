# Review of phase E3 (4837d64..c45202e), the Enable Banking consent plug-in

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3). The reviewer compared all four requests and their answers, field by field, with Enable Banking's published OpenAPI description and FAQ (reading only).

**No finding** of a request signed wrongly, of a sensitive value leaving the module, or of an answer read as a granted consent when it is not one. Compared with the documentation and without a difference: the list of Banks (its parameters and what is read of it); the start (every required field with its name and nesting; the form of `valid_until`; its arithmetic at the edges); the completion (the code sent; the session, its validity, the Bank and the accounts read; the lasting `identification_hash` as the reference, the session's own identifier kept only in the Bank Session); the ending of a session; the signed token (its claims, a lifetime under the maximum, made afresh for each request, never logged). Sound: parsing (a missing field, a wrong type, a null or a body that is not JSON gives a closed failure); `stateOf` (only the query, names decoded before comparing; two states, an empty one or a malformed one give none); the consent address must be https; an entry without the lasting value is never delivered, two with the same are both set aside; nothing sensitive in a log, a `toString` or an outcome (the Data Provider's own error texts never leave the plug-in); no contract call throws; the contract test runs the real requests and parsing; the module's dependencies.

## To fix in this phase, with the orchestrator's decisions

1. **CONFIRMED, latent until phase E5. An unattended request in a Fetch the Operator started is stored without its Bank Account** (`core/.../request/Gates.kt:102, 105`), so the count of Unattended Access never sees it, against ADR-001 §4.0 and UC-001 BR-012 (counted truthfully, whoever started it). The Bank Account is stored with every unattended request that names one; the test names one.
2. **CONFIRMED. A completion the Data Provider accepted but Slussen cannot use leaves a session open there that Slussen never learns of and never ends** (`EnableBankingConsent.kt:239, 258-266`): the session's identifier is read and thrown away when the validity, the Bank or the accounts cannot be used, and the Bank's consent stays open for as long as was asked. **Decision:** when the session's identifier is readable, the plug-in asks the Data Provider once, through the gate, to end that session before it answers; the outcome to the core stays "may have been granted, start again", whose text already tells the Operator that he can end a consent at his Bank. ADR-001 §4.1.1 says so (proposed as S-B-53).
3. **CONFIRMED. The return address is not checked** (`EnableBankingCredentials.kt:60, 79`): any text is stored, the Data Provider then refuses the start with a general code, and the screen cannot name the address. It is refused at the field unless it is an address with a scheme and without whitespace (the application's kind and an https address both pass), as UC-014 A1 asks for an entry Slussen can see is invalid.
4. **PLAUSIBLE. The device's clock is the only source of the validity asked for**: a clock that runs ahead by more than the request timeout makes every start a refusal with no reason shown. The time of the Data Provider's own answer to the list of Banks, sent just before, is used when it is earlier than the device's.
5. **PLAUSIBLE. Redirects are followed** by the module's client: a redirect of the start or the completion would send the state or the code to another host, in a request the gate never admitted. Redirects are not followed; such an answer is an unreadable one.
6. **CONFIRMED, minor.** A refusal without a code (a status in the 400s other than the one that asks to wait) at the completion is told as "may have been granted" when nothing was granted: it is a refusal.
7. **Tests.** The return address is among the planted values that must not be logged; a state given only in the fragment gives none; a redirect; a connection closed at the start; a slow answer at the start.

## Decided in the specification (S-B-53)

- An answer that carries both an error and a code is not understood, and nothing is sent (ADR-001 §4.1.1 said "not completed"; the builder's reading does not claim that the Bank refused).
- ADR-001 §4.0's sentence on requests without a sign of the Operator's presence applies to a Data Provider that needs a Bank Consent: SimpleFIN's requests are recorded as before (phase D5's tests unchanged).

## Not fixed here (for the question list, G-40)

- An answer's body is read whole, with no bound on its size.
- The signed token's time comes from the device's clock: a clock far off makes the Data Provider refuse the credentials, which is then shown as refused credentials.
- The codes `UNAUTHORIZED_IP` and `INVALID_HOST` (problems of the application's registration) are shown as a refusal by the Data Provider, without their own text.
- Changing only the return address means entering the key again.

## For phases E4 and E5 (in their prompts)

- E4: a start refused for its return address names the address that was sent; the credentials' form marks the return address as optional.
- E5: a selected Bank Account whose session identifier could not be kept (more Bank Accounts at one Bank than the Bank Session can hold) is told to the Operator with its reason; redirects are not followed in the Fetch either; the dates of a Fetch do not rest on a clock that runs ahead.
