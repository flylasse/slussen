# Review of phase W3-0 (commit 57b0a7a), the specification for Wave 3 (S-B-18..S-B-25)

Independent reviewer, read-only, a fresh context (Opus, as the writer: the plan's §5 row 3). Findings most serious first; the orchestrator's decision follows each where one was needed.

1. **Money safety, CONFIRMED: the duplicate S-B-21 closes is real, the rule closes it in the code, but Wave 4 is not told where it builds.** Real: the copy holds transactions dated from (first read − the old longest window − Matching Date Window) on, and a read with a cursor sends only the cursor (`YnabReader.kt:91`), so later reads never bring transactions dated before that start; a raise soon after the first read leaves days with no copy. Closed: `Comparison.readOne` works out `from` from the current settings, `readChanges` with `periodOwed` reads the period and then the changes, stored as one read, and `applyChangeSet` clears the flag only on success; a failed read, a moved cursor, refused credentials or a setting lowered again leave the flag set: one more read, nothing unsafe, nothing owed beyond the next successful read. **The gap:** UC-006 has no flow for it (A13 exists for First Upload Matching only); ADR-007 §3 says "the Budget is read first", against its own "otherwise the reason is shown and no plan exists"; UC-003 BR-016's "Until that read" grammatically covers only the settings case; the gate for the UC-013 case is new and not in UC-013. **Correction:** a UC-006 alternative flow (a Budget owes a read of its read period: no Upload Plan, the reason, the Comparison offered); drop "the Budget is read first" from ADR-007 §3; BR-016 says "after either case"; UC-013 names it. Recorded for Wave 4 as W4-09.
2. **Money safety, PLAUSIBLE: "for every served Budget".** `budget_read_state.change_cursor` is Not Null and `owePeriodRead` is an update, so it does nothing for a Budget never read; a literal builder might insert a row with a placeholder cursor, and `readOne` would then read changes since a bogus cursor. **Correction:** "for every served Budget that has a `change_cursor`; a Budget not read yet gets the longer period at its first read."
3. **Money safety and display, PLAUSIBLE: UC-010 step 5 with an owed read.** The statuses are worked out again at once from a copy that lacks the added days: Bank Transactions there become New, are counted and shown as waiting for an Upload, though they may already be in the Budget App; only the plan is blocked, and nothing on the screen says a read is owed. **Orchestrator's decision:** a change that owes a Budget a period read gives that Budget no statuses again from stored data. Its statuses stay as the latest Comparison left them, the Budget shows that a read of the Budget App is owed and why, and that read gives them. A mockup state shows it.
4. **PLAUSIBLE, low: lengthening without a period read.** The Matching Date Window is declared by the Budget App's part; a build that declares a larger one lengthens the read period and owes no read. Not corrected: recorded as G-30.
5. **CONFIRMED: UC-011 BR-008's date range has no end, and an empty Decision Journal has no start.** **Correction:** dated from (the oldest entry's day − the read period) up to today; with no entry, from today − the read period.
6. **Privacy, CONFIRMED (text), PLAUSIBLE (harm): UC-011 BR-007 against BR-008 for Import Identifiers.** BR-007 allows no identifier that the Budget App gives a transaction; BR-008 exports "the Import Identifier it carries" for every transaction, also those of an Other Import Path, which YNAB's own bank import or another importer wrote and which may embed a Bank reference. And Slussen's identifier without a Stable Reference is an unsalted digest of Source Key, date, amount, payee, memo and occurrence (ADR-008 §2): beside the date and amount of a coded export a guessed payee can be checked. **Correction:** only Import Identifiers that begin with Slussen's marker are exported; another one is marked as an import by an other path, without its value; BR-005 states the exposure that remains.
7. **CONFIRMED (gap): UC-011 A2 and BR-002 against UC-014 BR-005.** Missing credentials, or credentials already Refused, are not in A2's trigger, though the Budget App must not be contacted then; BR-002 does not say whether a refusal the export meets is stored. **Orchestrator's decision:** both are in A2's trigger without contacting the Budget App; a refusal the export meets is recorded as UC-014 BR-005 says, the one thing an export stores.
8. **PLAUSIBLE: the Decision Journal against the export (ADR-002 §9).** The read transaction is opened before the Budget App is read, so it is held across network reads; where the database's journal mode makes a reader block writers, every write and trim waits that long, and entries queued in memory are lost if the process dies. **Orchestrator's decision:** the export notes the newest entry at its start, reads the Budget App, then opens its read transaction and streams the entries up to the one it noted.
9. **PLAUSIBLE: switching the Decision Journal off.** "Recorded as the last entry before" leaves the order open with an asynchronous recorder: if `journal_on` is checked when the entry is written, the entry is dropped. **Correction:** the entry is queued before `journal_on` is stored, and that entry is never refused.
10. **CONFIRMED, low: `journal-export.html#complete`.** The caption says a transaction is named by its Bank Account and its Import Identifier; the entries shown carry none. **Correction:** show Slussen's Import Identifier in the entries.

No findings: the export changing stored state (BR-002 lists the copy, `last_read_at`, the cursor, balances and statuses; `comparison_pending` and `state_version` follow from nothing being stored); S-B-24's write that fails part-way; S-B-25 (the entity model, BR-005 and the code agree); the trimming rules; S-B-18; AGENTS.md §2.
