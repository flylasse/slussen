# Review of phase E5 (8a1c8be..d0a1bf1), the Enable Banking Fetch

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3). The reviewer compared each request and each field read with Enable Banking's published OpenAPI description and FAQ (reading only); the builder had read none of it.

**No finding** that invents a transaction, gets a sign or a date wrong, or contacts a Bank without a valid Bank Consent; nothing of this Data Provider can be Eligible without a Review Decision (no Stable Reference is ever delivered, Q-05). Compared with the documentation and matching: the two requests of a read and their parameters, paging, errors read from the code and not the status, every field of a transaction that is mapped, the balance types, the four codes that mark a consent refused (each means the session is gone; the codes about one account never mark it). Sound: the mapping (exact decimals; a sign, a space or an exponent unreadable; only a booked status stored, an unknown one unreadable; never the value date; the payee the other party; the memo's lines joined by one space with nothing trimmed or dropped); the same history twice (an overlap, another split of the pages, a third identical transaction, a pending one later booked: no second Import Identifier); paging (each page through the gate; a key used twice, a refused or failed page: nothing of that Bank Account); after a stop by the gate only complete reads are stored; the period shifted as a whole leaves no gap; no request without a handed session, the gate and readable credentials; Banks kept apart for A5 and A9; attendance, with A22 asked before any request and never in a Scheduled Fetch; SimpleFIN's path unchanged, the six changed tests each now assert A4 as specified; nothing sensitive logged.

## To fix in this phase, with the orchestrator's decisions

1. **CONFIRMED. One slow or failing request throws away the whole Fetch, Banks already read completely among them, and stops every other Bank** (`EnableBankingFetch.kt:331, 343`; `FetchTransactions.kt:430`). The Banks are read in the same order each time, so while one Bank is slow none is ever stored, and each attempt still spends the Request Limit and, where it counts, Unattended Accesses. The code follows ADR-001 §4.0's letter. **Decision (proposed as S-B-55):** what a Fetch read completely is always stored. A failure the Data Provider names for one Bank or one Bank Account fails that one and the Fetch goes on. A request that got no answer at all (a timeout, a lost connection) or an answer of the Data Provider's own failing ends the Fetch for what is not read yet, which is recorded as failed and not contacted.
2. **PLAUSIBLE, documented. The Data Provider's refusal of the period asked for has no rule**: many Banks give only a recent part of the history except shortly after a grant, and an account younger than the fetch period can be refused; the read then fails as an unreadable answer with the remedy "renew the Bank Consent", for ever. **Decision:** that code is a failure of its own for the Bank Account, with its reason (the Bank does not give the fetch period asked for) and its remedies (a shorter fetch period in Settings; or a Fetch soon after renewing). Nothing is retried with another period by itself. Whether Slussen should ask for the longest period the Bank gives instead goes to the question list (G-42).
3. **PLAUSIBLE. A failed balance request ends the Bank Account's whole read**, so that a Bank that does not serve balances is never read. A failure that concerns only the balance gives no Account Balance and the transactions are read; a failure that concerns the session or the Bank (A9, A5) keeps its meaning.
4. **CONFIRMED, low. A Bank Account that does not fit the Bank Session** gets the reason of an unreadable answer and the remedy to renew, which gives the same again; and one whose currency entry does not fit is dropped whole. It keeps its identifier without a balance where that fits, and what does not fit has a reason of its own (more Bank Accounts at this Bank than a Bank Session holds). A test that an earlier Bank Session without the currencies is read.
5. **PLAUSIBLE, low.** An answer with the status that asks to wait and another code keeps sending: the status decides. With a device language that cannot be sent, no header of presence is sent although the plug-in said it shows presence, so A22 is not asked for a request counted as unattended: what the plug-in says and what it sends agree. A Bank's Back-off counts from the Bank's answer, not from the start of the Fetch. The text for a Data Provider whose Bank Consent is granted but none of whose Bank Accounts is added says to add them.
6. **Tests.** One for each protection the review lists as unguarded (the session's Bank equal to its key; the core ignoring an outcome for a Bank it handed no session for; nothing read after a request to wait; the items above), and a planted Bank Account number, payee and memo in the test that nothing sensitive leaves.

## Decided in the specification (S-B-55)

- ADR-001 §4.1.1: the header that names the application carries the application's name (a plug-in is given neither the application id nor the version).

## For the question list (G-42)

- The documentation's pattern for an amount allows a minus sign; by W6-0's decision an amount with one is unreadable. A Bank that signs its outflows would have every outflow kept as an Unreadable Transaction: to settle when real data is seen.
- Decimals are accepted to thousandths for every currency.
- A Bank that rewrites a payee or memo, or moves a booking date, between two Fetches gives a second Bank Transaction, Needs Review; the first is never treated as gone, and nothing tells the Operator that the two may be one.
- An endless continuation is bounded only by the Request Limit.
- The Data Provider's code that the Bank asks the Operator to act is shown as an unreadable answer.

## Owed

- Wave 4 (W4-12): at review, a Needs Review Bank Transaction that differs from one already uploaded for the same Bank Account only in its payee or memo text, or only in its date within the Budget App's Matching Date Window, is shown with that hint, so that the Operator does not approve a duplicate unknowingly.
- Phase E6: the limit's refusal of a balance read does not stop the transactions read of that Bank Account; the accesses a Fetch spent are counted also when it then failed.
