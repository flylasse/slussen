# Review of phase D2 (68f11db..9de17be), Import a Transaction File in the core and in storage (UC-002)

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3). Every case was worked through `TransactionFileCounting.count` by hand and with a small simulation.

**No findings** on: the cases of survey risk R1 for the HSA format, whose references are all Derived (the same file twice; an overlapping later file; a pair in one file; a pair after one stored with a Stable Reference, and the reverse; three identical lines over two files in each order; a pair, then the pair and a third; a reference another Bank Account holds; a stored transaction with a Review Decision, a Transfer Leg or of a Retired Account): none gets a second Import Identifier, loses or changes a Stable Reference, is dropped or is absorbed against UC-002 BR-003. "Identical" compares what O-1 compares for a Fetch (ADR-008 §2), and the occurrence numbers are allocated as O-1 allocates them. Lines not booked or of amount 0 take no part in the counting. Everything that decides an outcome is inside the one function that the Room store and the fake both call; the SQL reads a Bank Account's rows without a filter or limit, and the inserts cannot violate the table's unique indexes. One transaction holds the inserts, `state_version` and the `transaction_file` row; a collision writes nothing. Admission in Normal only; a Comparison that fails keeps the import; entries of the Decision Journal hold no payee or memo and never block; the rejection reason is cut, stored and shown, never logged. The builder's three visible assumptions agree with the specification.

## To fix in this phase, with the orchestrator's decisions

1. **CONFIRMED. A Supplied reference shared by two lines of a file brings them in again at every later import** (`TransactionFileCounting.kt:67, 86-99`). The code follows UC-002 BR-003 step 2 as the correction of W5-0 (its item 11) worded it, and that wording is the defect: the orchestrator's own. Case: a file holds two lines with the Supplied reference `BANK-10`; the first import stores both without a Stable Reference; the same file again: step 1 finds no stored Stable Reference, step 2 skips both because they are Supplied, step 3 stores two more with new occurrence numbers. Not reachable with the HSA format (Derived only), reachable by any File Format that supplies references. **Decision:** step 2 leaves out only a line with a Supplied reference that no other line of its file shares (that one is new: its reference names it); every other line left by step 1 is counted against the stored identical Bank Transactions without a Stable Reference. UC-002 BR-003 and the row S-B-30 are amended; a test imports such a file three times.
2. **PLAUSIBLE, low. The outcome after a store that failed does not say whether the file was recorded** (`ImportTransactionFile.kt:114-115`): if the second write (the Rejected record) fails too, the screen cannot say whether the Source Health now shows the failure. The outcome carries it.

## For Wave 4 and the question list, not fixed here

- **The same history gives different Import Identifiers when it was cut into files differently** (UC-002 BR-003 step 3, as specified). Case: one line X in a first file, then X twice in a later one, gives one transaction named by its Stable Reference and one by its occurrence; the whole history in one file gives two named by occurrence. After a new installation that imports the whole history at once, the Upload of the first is not found by its Import Identifier. It is no silent duplicate (the second is Needs Review and resembles a transaction Slussen entered), but First Upload Matching is weaker for a file-imported Bank Account than ADR-008's consequences say. Owed to Wave 4 as W4-10, and to the operator's list as G-36.
