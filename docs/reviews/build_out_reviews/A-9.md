**No findings** on: every field the file holds (the Budget App part maps only names, date, payee, memo, amount, and an Import Identifier only when it carries Slussen's marker; no reference of the Budget App is written; the codes are numbered per export from a table thrown away with it, so they cannot be turned back from the file; the reasons of A2 are Slussen's own words; the JSON is well formed on every path and no failing path leaves a file presented as complete); nothing stored (the read's cursor is thrown away, the gate keeps no counter, and `anExportChangesNothingStored` compares enough to fail on any write); the paging (no page skipped or written twice, it stops at the bound noted, which is noted on the Decision Journal's own thread); admission and refusal as ADR-007 §2 says, and no lock shared with `DecisionJournal`'s order, `JournalQueue` or a queued clearing; the document (every outcome that is not complete removes it, the stream is closed once, a second export is blocked); the tests named after a protection fail when it is removed; markers.

## To fix in this phase, with the orchestrator's decisions

1. **PLAUSIBLE. An export of a busy Decision Journal at its size limit may never complete.** `JournalExport.kt:294-316` reads pages and fails, removing the file, when the entry it last wrote has been trimmed away. Case: the Decision Journal is at its size limit (its usual state after long use) and a Fetch records 500 or more entries while the entries are written; each trims an oldest entry; the export fails, and fails again whenever a large Fetch overlaps. UC-011 has no such flow, and BR-007 says "as the Decision Journal holds them when they are written". **Decision:** short reads stay (a read transaction over the whole export would hold every write of the Decision Journal for its length on Android before 15, against UC-010 BR-004), and the export completes with what the Decision Journal still holds: the entries removed between two reads, by the size limit or by a clearing, are left out, and the file's closing part and the screen's answer say how many of the entries noted at step 3 were removed while the file was written. Proposed as S-B-28 (ADR-002 §9: short reads bounded by entry ids instead of one read transaction; UC-011 BR-007: the closing part's count of entries removed while written).
2. **CONFIRMED. `journal.db` is opened in Room's default journal mode**, write-ahead logging on most devices (`SlussenDatabases.kt:51-54`), while `slussen.db` and `device.db` are set to `TRUNCATE` and the start sequence (`StartSequence.kt:24, 74`, `setAside`) knows only `journal.db` and `journal.db-journal`. Case: `journal.db` is judged unreadable and set aside, its `-wal` stays beside it, a new `journal.db` is created and the old log may be replayed into it; the original is not kept whole (ADR-002 §8 step 5). The size the limit trims against does not count the log either. Older than this phase. **Decision:** `journal.db` is opened with `TRUNCATE` as the other two, as ADR-002 §1 describes its files; the start sequence also moves a `-wal` and a `-shm` left by an earlier build when it sets a database aside.
3. **PLAUSIBLE. The tests of planted values cover only entries of a Comparison.** `UC011ExportTheDecisionJournalTest.kt:429, 446`: the planted Bank Account number and fingerprint sit in a stored Bank Account the export never reads, so those assertions cannot fail; entries written by a Fetch (`FetchTransactions.kt:523`), entries of Account Mapping changes and the stored copy of A2 with codes on are not exercised. The tests are extended to every kind of entry the code records and to A2 with codes.
4. **CONFIRMED, minor. BR-008's branch "with no entry" can be reached and is not followed.** The precondition is checked when the screen opens; a clearing with the Decision Journal off (it records no entry), or a trimming to nothing, before the place is chosen leaves no entry at step 3, and the code answers "nothing to export" (`JournalExport.kt:115`) where BR-008 says the Budget App's transactions from the day of the export back by the read period. The branch is followed.
5. **CONFIRMED, minor. The save dialog** (`SlussenActivity.kt`, `JournalExportRoute`): the document's name is read from its provider on the main thread; `picker.launch` is not guarded against a device with no documents app, which would crash and leave "choosing" set (NFR-023). Both fixed, the second with its answer at the control.
6. **PLAUSIBLE, minor. The screen waits for the Decision Journal's queue** (`JournalExportViewModel.kt:62`), as Settings did before the fixes of A-8: "Choose where to save" stays disabled behind a long trim or a Fetch's queued entries. And while the export waits for the lane behind a Fetch the screen says "Reading YNAB…" and offers no way back. The action is enabled as soon as an entry is known to be held; the waiting is named as waiting and can be left.
7. **PLAUSIBLE, edge.** A task of `JournalQueue.queue` that throws an `Error` never completes its result, so an export would stay on "Reading…": the result is completed with the failure.
