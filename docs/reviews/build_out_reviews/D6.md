# Review of phase D6 (68e4582..219742a), the worker, the Fetch Schedule and the New Transaction Notification

Independent reviewer, read-only, a fresh context (Opus, as the builder: the plan's §5 row 3).

**No finding** that fetches when the Operator was promised it would not, spends a Request Limit beyond the Fetch Schedule, asks the device for a permission outside ADR-001 §5, or puts anything but the number on the lock screen. Sound: the permissions (the merged manifests of debug and release hold exactly the list; the receiver permission of the application's own id was in the check before this phase; no foreground service and nothing that asks for one; what the libraries merge in beyond permissions is not restricted by the specification); the scheduling (a start keeps work of the same period, so no start postpones the next run; the first delay equals the period on every path; one unique periodic work; the only constraint a network connection); the worker's process (one start for a process, on stored data only; a cancellation is passed on, not swallowed); the notification (changed only when the number differs; a silent, low channel; an explicit, immutable intent; the number only); the question (once, and no dialog at each opening); the dependency.

## To fix in this phase, with the orchestrator's decisions

1. **PLAUSIBLE. The notification after a Scheduled Fetch is not part of the worker's run** (`ScheduledFetchWorker.kt`, `CompositionRoot.kt:184`): it is updated by a follower of the operations that end, and the worker answers before that has read the number. Case: the device is asleep, a Scheduled Fetch stores new transactions, the worker answers, the device suspends: the notification shows the old number until the device wakes. The worker updates the notification itself before it answers (UC-001 A12 step 3).
2. **CONFIRMED. A switched-off channel counts as notifications allowed** (`AndroidNotificationDevice.kt:227`): the line of `settings.html#notifications-off` is not shown when the Operator switched off only Slussen's one channel. The channel is checked too.
3. **CONFIRMED. Settings can show a next Scheduled Fetch for a Fetch Schedule the Operator just changed** (`SettingsViewModel.kt`): after a reschedule or a cancel that failed, the note is dropped at the next reload and the old work's time is shown, also beside a stored Fetch Schedule of 0. The note stays until a start or a later change has set the work.
4. **CONFIRMED. Tests that cannot fail.** No test reaches the worker's answer (a retry on failure would pass every test); the fake of the scheduled work holds one work by construction; what the notification holds beyond its text (the channel's importance, no sound, no further text) is tested nowhere. The worker's answer and what the notification holds are each decided by plain code a JVM test asserts, and the Android classes only render it.

## Decided in the specification

5. **A run the device held back can start in the first seconds of an opening** (after a force-stop or in a restricted standby bucket the device releases overdue work when the app comes to the foreground). It is never sooner than a period after the Fetch Schedule was set. **Decision:** no guard (it would need a time limit of Slussen's own choosing); UC-001 BR-013 says that such a run is a Scheduled Fetch, never a Fetch at the opening, and that Slussen shows that the Fetch Schedule started it. To the question list (G-38).
6. **The number leaves out a Bank Account mapped into a Budget that is no longer served**, which BR-014's first sentence included and its later sentence and the mockup did not. **Decision:** the code stands; BR-014 says "mapped into a Budget Slussen serves".
