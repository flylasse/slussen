# Phase A-6: every Operator Setting on Settings

Read `_common.md` in this folder first. Survey: `docs/reviews/build_out_sweep_A_screens_settings.md` (§2 UC-010, §3 row A-6, §5, §6 risks 3 and 5). The specification of this wave: the S-B-nn rows of phase W3-0 in `docs/build_out_plan.md` §6.

Read also: UC-010 in full; the entity model's OPERATOR_SETTINGS; ADR-002 §3 (O-13 `SettingsStore.*`); ADR-006 (Detailed Logging); NFR-023; the mockup `settings.html` (every state); the fetch period's editor as it is built (`:core` `settings`, `:app` Settings), which is the pattern; phase B4's engine `Comparison.statusesAgainAfter`.

Build:
1. In `:core` and `:persistence`: every scalar Operator Setting that has no editor yet, with its range and default as UC-010 and the entity model state them, stored through O-13 (one transaction each, raising `state_version`, journaled with the value before and after, UC-011 BR-001), a value outside its range refused with the range (A1), a write that fails answered "not stored".
2. UC-010 step 5: a changed setting that the Comparison or the Transfer detection reads gives the statuses again through `Comparison.statusesAgainAfter` (the marker set in the setting's own storage transaction), never a second path.
3. A5: Detailed Logging read by the app's log from the stored setting (today it is hard-coded off), as ADR-006 says; A9: Upload as Cleared as a switch (its effect comes with Wave 4); A6: the Fetch Schedule's line as far as UC-010 states it here (its behaviour is Wave 5).
4. In `:app`: the Settings sections of the mockup with an editor per setting, each showing its state at its own control, its answer in the same place, and never a crash.
5. Tests first: core tests per setting (range, default, stored, journaled, refused, the statuses given again where they must be and not where they must not); ViewModel tests for every editor state with a failing store; a screen IT for one numeric editor and one switch.

Not in this phase: the description lists (A-7), the Decision Journal's control (A-8), the export (A-9), Start Over (Wave 7).

First, from the review of this wave's specification (`docs/reviews/build_out_reviews/W3-0.md`, items 1 to 3; S-B-21 as amended):
- A change that lengthens the read period (the longest of the fetch period, the Upload Window and the file upload window is raised) sets `period_read_owed` for every served Budget that has a `change_cursor`, in the setting's own storage transaction, and never writes a row with a made-up cursor.
- While a Budget owes a period read, no conclusion from stored data changes its Transaction Statuses: not UC-010 step 5, not UC-009's status-again, not the conclusion of a marker left for another reason (ADR-007 §3a, UC-003 BR-016). Build that guard once, in phase B4's engine and the conclusion it calls (`Comparison.statusesAgainAfter`, `recomputePending`), so that it also covers the UC-013 case (a served Budget that gains a Budget Account); only a Comparison that reads the Budget with its period gives the statuses again. Tests name each case, among them: a lowered setting does not clear the flag; a read that fails leaves it; the Budget shows that a read is owed (the read model carries it for the screens of `settings.html#saved-read-owed` and `budget.html#period-read-owed`).
- Do not build W4-09 (no Upload Plan while a period read is owed): Wave 4 builds it. Do not make it harder: the fact must be readable from the core.
