# Phase A-11: Start Over (UC-010 A12, FR-107)

Read `_common.md` in this folder first. Survey: `docs/reviews/build_out_sweep_A_screens_settings.md` (§2 "Start Over", §3 row A-11, §4 question 5). The specification as it stands: UC-010 A12 (rewritten by S-B-48: Slussen first asks the Data Provider to end each Bank Consent, then deletes everything, whatever the answers, and names each Bank whose consent was not confirmed as ended), FR-107, UC-006 BR-017 (after a new installation nothing is uploaded until First Upload Matching is confirmed), UC-007 A7 (ending a Bank Consent), ADR-002 (§1 the files Slussen stores; §3 the operations, each all or nothing; §6 the start and when a First Upload Matching is opened; §8 unreadable data, the last good copy, the originals set aside; §9 the Decision Journal), ADR-006 (the Keystore's key and the credentials), ADR-007 §2 (the admission table: Start Over has no row yet).

This phase writes a small part of the specification first, then builds it. Under `docs/` you may change exactly: a state for Start Over in the mockup `settings.html` (the statement of what is deleted with its numbers, the confirmation, the result that names the Banks whose consent was not confirmed as ended) with its row in `mockups/index.html`; ADR-002 §3 (one new operation for Start Over: what is deleted in which order across `slussen.db`, `device.db`, `journal.db`, the stored credentials and their key, the last good copy and the originals set aside, and what is true after a process that ended part-way: Slussen must never be left half deleted in a way that could upload again without First Upload Matching); ADR-007 §2 (its row: admitted only in Normal with nothing else running; what it does to a Scheduled Fetch that is due or deferred, to a Consent Request under way and to an import or export in progress); UC-010 A12 only where it is silent on something you must build (the scheduled work is cancelled and the New Transaction Notification removed; what the Operator sees when Start Over cannot be done now); and rows S-B-57 onwards in `docs/build_out_plan.md` §6, one per change. AGENTS.md §2 applies; no new requirement, use case or Operator Setting; no schema change.

Build, in `:core`, `:persistence`, `:app` and `:testing`:
1. The statement (UC-010 A12 step 1) with its numbers from stored data, and the confirmation: a destructive action that cannot be undone, confirmed in a way a slip of the finger cannot make (as the mockup you draw shows; no typed number or phrase of Slussen's own invention unless the mockup pattern of the app already has one: look at how clearing the Decision Journal confirms).
2. The operation: ending each Bank Consent at its Data Provider first (through phase E2's `BankConsents`, each through the gate, attended; a failure or a missing credential does not stop Start Over and is named in the result), then the deletion as ADR-002 now states it, in an order that is safe at every point where the process could end: the marker that a First Upload Matching is owed is in place before anything that could let an Upload happen is gone, and a start after an interrupted Start Over finishes it or leaves a state that is plainly a new installation. The scheduled work is cancelled, the notification removed, nothing of the old data stays in memory (ViewModels, the holder of consent answers, the import's state).
3. Afterwards Slussen is as newly installed: the first-run Overview, a First Upload Matching open (UC-006 BR-017; Uploads are not built yet: the state is stored as a new installation stores it), a new installation's default settings and description lists.
4. Tests first: core tests for the statement, the admission, each Bank Consent's ending (confirmed, not confirmed, not reachable, no credentials) and the result's list; a test with a store that fails at each step of the deletion (what the next start finds and does); persistence ITs (written, compiled) that after Start Over each database holds what a new installation holds and no file of the old data is left (the last good copy and set-aside originals among them); ViewModel tests for each state. A test that after Start Over, with the same Bank Transactions fetched again, nothing is Eligible for an Upload before First Upload Matching (as far as the stored state decides it without Uploads).
