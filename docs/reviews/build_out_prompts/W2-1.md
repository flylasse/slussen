# Phase W2-1: storage, `slussen.db` version 6

Read `_common.md` in this folder first. Surveys: `docs/reviews/build_out_sweep_B_decisions.md` (§2 B1, §5 R3), `docs/reviews/build_out_sweep_C_uploads.md` (§1 Tables, §2 C1, §5 risk 3) and `docs/reviews/build_out_sweep_D_file_import_scheduled_fetch.md` (§2 D1).

Read also: `docs/build_out_plan.md` §3 (one version 6 for every remaining table) and §6 (the S-B-nn rows of phase W2-0); the entity model in full; ADR-002 in full (§2 the tables and the technical tables, §3 the storage operations, §7 schema versions and Migrations, §8); `persistence/` as it is: `SlussenDatabase.kt`, `SlussenMigrations.kt`, `MainDaos.kt`, the committed schema files, `SchemaVersionCheckTest`, `SlussenDatabaseMigrationTest`, `SlussenDatabaseMigrationIT`, `StoredPartsTest`, `SlussenStorage.MAIN_VALUES`.

Build, in `:persistence` only (with what `:core` ports and `:testing` need to compile):
1. `slussen.db` version 6, with a hand-written `MIGRATION_5_6` and the committed schema file `6.json` (copy the file Room generates): every table the entity model and ADR-002 §2 name that version 5 lacks (`review_decision`, `upload_plan`, `eligible_transaction`, `upload_plan_item`, `sent_record`, `transfer_counterpart`, `transaction_file`, and any other you find missing), each exactly as the entity model states it (attributes, optionality, values, constraints, foreign keys, indices), and the change to `transfer` that phase W2-0 specified (an optional side). Rebuilding `transfer`, which `bank_transaction` references, inside a Migration must keep every row and every reference: follow SQLite's documented procedure for a table rebuild with foreign keys.
2. Version 5 is now final: pin it in `SchemaVersionCheckTest`, and extend the JVM migration tests and the instrumented `SlussenDatabaseMigrationIT` for 5 to 6 with rows in every table (invented data), among them Transfers with their Transfer Legs.
3. Entities and DAOs for the new tables with the plain reads and writes later phases will build on; the new value columns added to `SlussenStorage.MAIN_VALUES` (ADR-002 §8 step 1). No storage operation of ADR-002 §3 (O-6 onward, O-12, O-13) is built here: each comes with its use case's phase, and none of the core's rules changes.
4. `state_version` (ADR-007): the survey of the Uploads found that only O-1, O-4 and O-5 raise it. Every storage operation that changes what an Upload Plan was prepared from raises it (mappings, settings, connections, description lists, decisions): add that to the existing operations, with a persistence test per operation (instrumented where it needs the real database, and a JVM test where the fake can show it).

Tests first where the JVM can run them (the migration tests, the schema check). Say which you saw fail first. The instrumented tests compile and are read with care, since nobody runs them here.

Not in this phase: any use of the new tables by the core; `device.db` (Wave 6).
