# Phase W6-0: the specification for Wave 6 (Bank Consent and Enable Banking)

Read `_common.md` in this folder first. This phase writes the specification and no code: you may change files under `docs/` (use cases, entity model, glossary, requirements, ADRs, mockups) and the table "Specification changes (S-B-nn)" in `docs/build_out_plan.md` §6 (continue the numbering after the last row), and nothing else.

Survey: `docs/reviews/build_out_sweep_E_enable_banking_consent.md`, all of it (§1 what is built, §2 the gaps G1 to G15, §3 issue #7, §4 issue #15, §5 the phases, §6 the facts about Enable Banking's API that the design assumes without proof, §7 the safe guesses, §8 the risks R1 to R6, §9 the questions).

The operator's answers, in `docs/build_out_plan.md` §6: Q-02 (the return address: a custom address, `slussen.app://consent` and `slussen.app.debug://consent` for debug builds, with pasting the address back as the fallback), Q-03 (one country, the chooser starting at the phone's), Q-05 (issue #7: a missing Stable Reference stays doubtful; every such Bank Transaction is Needs Review; a Bank's references are trusted only after the operator has seen real ones: so the survey's option 1, and no phase E7), Q-15 (Enable Banking's documentation may be read: this environment reaches `enablebanking.com`).

**Check the facts first.** The survey's §6 lists what the design assumes about Enable Banking's API without proof (how an authorisation is started and completed, the session and its validity, whether an account's identifier is the same across sessions, the headers by which a request counts as attended, balances and their kinds, transactions and their paging, references, error codes, the list of Banks by country). Read Enable Banking's public documentation (`https://enablebanking.com/docs/`: the API reference and its guides) for each of them before you write a rule that rests on it, and record in your report, fact by fact: confirmed (with the page), different (what the documentation says instead, and what you wrote because of it), or not found (then write the most conservative rule and list it under Open). Use no credential and call no API; reading documentation only. If the documentation cannot be reached, say so first in your report, write only what does not rest on those facts, and list the rest under Open.

Read also: UC-007 in full; UC-001 (A4, A5, A9, A13, BR-012, BR-016); UC-013 (BR-011, BR-012) and UC-009 BR-004 (how a Bank Account is recognised again); UC-014 (credentials of a Data Provider); UC-008 (Blocked Reasons, the consent warning); UC-010 (the consent warning lead time; A12 only as far as G13 needs); the entity model (BANK, BANK_CONSENT, BANK_SESSION, CONSENT_REQUEST and its correlation, PROVIDER_REQUEST); ADR-001 §4.0, §4.1 (the Data Provider contract and `BankConsentCapability`), §5; ADR-002 (O-10, `device.db`, its backup rule: never backed up); ADR-005 §5 (the application ids of debug and release); ADR-006; ADR-007 §2, §3 (a Consent Request and Upload preparation); NFR-004, NFR-008, NFR-012, NFR-022; C-006, C-007; the mockup `consent.html`; the architecture rules K-04 (no Data Provider's name in `:core`, `:persistence` or the screens) and K-15. And the plan's rows G-01 onwards and S-B-01 onwards, so that nothing settled is settled again differently; Wave 5's Scheduled Fetch as built (`docs/reviews/build_out_reviews/D5.md`), since Unattended Access counts its requests.

Write, each as its own S-B-nn row in the plan and in the specification itself:
1. **The contract** (ADR-001 §4.1), from G1, G4, G5, G9, G10: how the Banks a Data Provider reaches are learned (by country; a request through the gate), what names a Bank (G2: so that two Banks of one name in two countries are never one), who reads the state of an answer, what validity is asked for, that a Bank Account's reference must be the same across sessions and renewals (and what the plug-in does when the provider's own identifier is not: risk R1), and how the Operator's presence is told to the Bank (risk R2), each as the documentation supports it.
2. **UC-007's missing steps and flows** (G1, G3, G6, G7, G8, G15): choosing the Bank; the return address (Q-02: its form for debug and release, how the Operator learns the exact address to register, the paste-back fallback and when it is offered, that it needs no device permission); a failure in transit at the start, the completion or the revocation; a refusal by the gate; no answer ever (the Operator abandons the Consent Request: its step, and ADR-007 §3); no browser on the device; a completion refused after the answer was taken; where a refusal is shown when the Bank has no Bank Account yet; how "treated as expired from now on" (A9) is stored. The mockup states G15 lists, written into `consent.html`.
3. **Storage** (for phase E1): `device.db` version 2 with what the entity model already describes for Bank Consents, and only what items 1 and 2 need beyond it (G2, G8), each column with its reason. `slussen.db` stays at version 6: if G2 seems to need a change there, choose the reading that needs none (the Bank's reference carries the country) and say so.
4. **The Enable Banking Fetch** (for phase E5; G11, G12, risk R5): which balance is the Account Balance and its sign, and the mapping of a transaction's fields (date, sign, payee, memo, booked or pending, the reference: Q-05), each stated as a rule with what happens when the field is missing (UC-001 BR-016: nothing is completed by guessing); paging through the gate; A4, A5 and A9 for each Bank.
5. **Unattended Access** (for phase E6; UC-001 A13, BR-012, C-006): what is counted, for what, over what time, as the documentation and PSD2's limit support it, and how Slussen's own count relates to the Bank's (risk R2).
6. **G13 and G14**: what removing a Data Provider's credentials and Start Over do to Bank Consents (ask the Data Provider to end them first, or not: the most conservative reading that never leaves a consent the Operator believes ended), and that every text and address stays free of a Data Provider's name where K-04 forbids it.
7. Anything else the survey's findings show to be contradictory between UC-007, UC-001, UC-013, the entity model, the ADRs and the mockups, settled by the most conservative reading, and anything Wave 6's builders would otherwise have to guess.
