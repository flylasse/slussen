# Phase W5-0: the specification for Wave 5 (Transaction File import, Scheduled Fetch, the New Transaction Notification)

Read `_common.md` in this folder first. This phase writes the specification and no code: you may change files under `docs/` (use cases, entity model, glossary, requirements, ADRs, mockups) and the table "Specification changes (S-B-nn)" in `docs/build_out_plan.md` §6 (continue the numbering after the last row), and nothing else.

Survey: `docs/reviews/build_out_sweep_D_file_import_scheduled_fetch.md`, all of it (§1 what is unbuilt, §2 the phases, §3 the questions, §4 the safe guesses S1 to S10, §5 the risks R1 to R5).

The operator's answers, in `docs/build_out_plan.md` §6: Q-01 with "the format" below the table (the HSA's CSV export, described from the operator's sample with invented rows; the sample itself is not in the repository and must not be asked for), Q-14 (Scheduled Fetch and the notification: four permissions, roughly even spacing, starting as soon as the build is installed, the notification permission asked once on the Overview). The survey's questions 1, 3, 4, 5 and 6 are answered by these; question 2 (the fields of the derived reference) is answered by Q-01's format description as far as it goes, and otherwise by the survey's recommendation.

Read also: UC-002 in full; UC-001 (A11, A12, A14, BR-005, BR-012, BR-013, BR-014) and UC-003 BR-008 (Import Identifiers) and A1; UC-010 A6 (the Fetch Schedule) and its mockup rows; UC-013 A4 (a File Format's Bank Account); the entity model (TRANSACTION_FILE, FILE_FORMAT, FETCH `started_by`, OPERATOR_SETTINGS `scheduled_fetches_per_day`, `scheduled_fetch_deferred`); NFR-007, NFR-022, NFR-023; ADR-001 §4.3 (File Pre-processors) and §5 (device permissions); ADR-005; ADR-007 §1, §2 (operations and their origins); ADR-008 §4 (permanence of identifiers); ADR-002 §3 (O-3 `FileImportStore.importWhole`, built in phase W2-0: read its code in `:persistence` and its review `docs/reviews/build_out_reviews/W2-0.md`); the mockups `import-file.html`, `overview.html`, `settings.html`. And the plan's rows G-01 onwards and S-B-01 onwards, so that nothing settled is settled again differently.

Write, each as its own S-B-nn row in the plan and in the specification itself:
1. **The HSA CSV format** where a File Pre-processor's format belongs (ADR-001 §4.3 or the place the survey names): the layout of Q-01's description in business terms (which lines are transactions, which are skipped and why, the date and amount forms, what a pending or summary line is), what makes the whole file rejected, and the recipe of the derived reference, stated as final (ADR-008 §4: an Import Identifier is permanent, so the recipe never changes once a file was imported). The recipe must make an overlapping later export of the same Bank Account give the same references for the same transactions (no line number, nothing that shifts between exports). Use invented values only.
2. **UC-002's gaps**, by the survey's safe guesses S1 to S7: references across files (S2, with risk R1: say plainly how a later file's lines are counted against stored Bank Transactions so that no transaction gets a second Import Identifier), the meaning of the file's transaction count (S3), the currency of a line (S4), a known transaction with changed text (S5), where an import starts and A7 (S6), a Comparison that fails after an import (S7), the rejection reason's length and privacy (S1).
3. **NFR-022 and ADR-001 §5**: the device permissions the Scheduled Fetch and the notification need, each with what it is for, as Q-14 allows; nothing beyond them. Say that the release permission check (`build-logic`) follows this list and nothing else (risk R3).
4. **The Scheduled Fetch** (UC-001 A12, A14, BR-005, BR-013, BR-014; ADR-007): its timing (Q-14 and survey question 5, option a: evenly spaced from when the schedule is set, the device may shift it; no clock time, which would be a new Operator Setting), that it starts by itself after an update when the stored setting is above 0, what it does when an Upload Plan is open or an Upload is written (deferred, started when that ends), that it is never retried and never prepares or writes an Upload, how its requests count (unattended), and what happens to a notice of a Scheduled Fetch that failed when Slussen was not open (risk R4: decide by the most conservative reading whether it must survive the process, and say where it is kept if so, using only stored data the entity model already has; if a new column would be needed, say so under Open and choose the reading that needs none).
5. **The New Transaction Notification**: what it counts, when it is shown, updated and removed, what a tap does (S9), and when the permission is asked (Q-14: once, on the Overview, when the Fetch Schedule is above 0), with the passive line when notifications are off. The mockup states the survey found missing (the permission ask, A7's entry), written into the existing mockups.
6. **The leftovers** (S10, issue #16 as the survey reconstructs it): a Fetch of one Budget, as far as the specification already has it; no new screen.
7. Anything else the survey's findings show to be contradictory between UC-001, UC-002, UC-010, the entity model, the ADRs and the mockups, settled by the most conservative reading, and anything Wave 5's builders would otherwise have to guess.

Not in this phase: Enable Banking and its Unattended Access (A4, A9, A13: Wave 6); Uploads (Wave 4, which is built after Waves 5 and 6: the specification written here must not assume that Uploads exist, and must not contradict the rows W4-01 to W4-09 the plan owes to Wave 4).
