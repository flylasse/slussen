# Phase D6: the worker, the Fetch Schedule and the New Transaction Notification

Read `_common.md` in this folder first. Survey: `docs/reviews/build_out_sweep_D_file_import_scheduled_fetch.md` (§1 "Device permissions and components", §2 row D6, §3 questions 3 to 6, §4 S8, S9, §5 R3, R4). The specification: NFR-022 and ADR-001 §5 as they now stand (S-B-37), UC-001 BR-013 and BR-014, UC-010 A6, the rows S-B-37 to S-B-39 in `docs/build_out_plan.md` §6 with `docs/reviews/build_out_reviews/W5-0.md`, ADR-005, and the mockups `overview.html` (the notification and the permission question) and `settings.html` (the Fetch Schedule, notifications off).

Read also: phase D5's code and review; `build-logic`'s check of the release permissions and its tests; how the app builds its services (`CompositionRoot`, `UiServices`), since a worker runs in a process where no screen was opened.

Build, in `:app`, `:core` (the count the notification shows) and `build-logic`:
1. The periodic work: scheduled from the Fetch Schedule as S-B-38 says (evenly spaced from when it is set, started by itself when the stored setting is above 0), rescheduled when the setting changes, cancelled at 0, a network constraint only, never retried; it calls phase D5's `scheduledFetch()` and nothing else.
2. The permissions: exactly the list of NFR-022, in the manifest and in the check of `build-logic`, with anything a library adds beyond that list removed in the manifest; the check fails for one more or one less. Do not widen the check beyond NFR-022: if the build cannot pass with that list, stop and report.
3. UC-010 A6 on the Settings screen: the Fetch Schedule's editor with its range and the approximate next time, as the mockup shows.
4. The New Transaction Notification: its count as a function of `:core`, shown, updated and removed as BR-014 says (after every operation ends, and at a start), the tap, the permission asked once on the Overview and the passive line when notifications are off.
5. Tests first: JVM tests of the scheduling decisions (what is scheduled for which setting; behind an interface a test can replace), of the count, of the ViewModels; the `build-logic` test of the permission list; a worker test with the library's test support if the module's tests can reach it, otherwise an instrumented test (written, compiled). Say plainly in your report what only a device can show.
